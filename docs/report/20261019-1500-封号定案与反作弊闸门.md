# 封号定案与反作弊闸门（2026-10-19 15:00）

## 一句话

**在有反作弊的场次里，本工具不再碰游戏进程一个字节。** 默认 `-freeze off`，
检测到完美 / 5E / Faceit / EAC / BattlEye / Vanguard 就直接拒绝所有进程访问，
退化成纯抓包。代价是**不出目标**；这是刻意的取舍。

---

## 一、触发这件事的那句话

2026-10-19 14:55，用户现场反馈：

> 「上次读取完账号被封禁了」

关键点在「**读取完**」三个字，以及那次操作**冻结时间很短**（不是 21:01 那次的 1979 ms）。
这直接推翻了此前四轮排障得出的全部安全结论。

## 二、归因演进：三版全错，第四版定案

| # | 时间 | 当时的归因 | 判定 |
|---|---|---|---|
| 1 | 10-17 21:01 | 默认 `-freeze full` = 冻结 1.979 s，所以是「冻结这个动作」有问题 | ✗ 反汇编原版 v2.0.5，它也是 `NtSuspendProcess` |
| 2 | 10-18 | 冻结动作不是主因，真因是「冻结期间读了多少内存」 | ✗ `ReadProcessMemory` 只在本机内核发生，不经驱动上报 |
| 3 | 10-19 09:39 | 真因是「挂起全部线程 1979 ms，把反作弊心跳线程冻住了」 | ✗ 10-19 现场用很短的一次冻结复现了封号 |
| 4 | 10-19 15:00 | **只要碰了进程就会被看到，跟时长无关** | ✓ 定案 |

### 为什么第 4 版才对

完美平台的防护栈（见 `2/report/20261019-完美平台反作弊分析.md`）：

```
Ring-1  Hypervisor (SHV)          影子页表 / EPT，看得到一切内存映射
Ring0   ObRegisterCallbacks 等     ★ 句柄级回调：谁打开 cs2.exe、要什么权限，实时上报
Ring3   PacNova                   用户态扫描 + 心跳
```

**`ObRegisterCallbacks` 是决定性的那一层。** 它挂在进程对象上，
`OpenProcess(cs2.exe, PROCESS_VM_READ)` 这个调用**在返回句柄之前**就已经被回调看到了。
也就是说：

- 我们「只读、不注入、不建远程线程、不写内存」这些底线，**防不住它** ——
  它不需要看到你读了什么，只需要看到你**打开了**。
- 冻结时长从 1979 ms 压到 350 ms，**也没有意义** —— 被记录的是「发生了一次挂起」，
  不是「挂起了多久」。

封禁粒度是 **HWID**（CPUID + MAC + 卷序列 + 机器 UUID），**换号无效**。

## 三、落地：三道闸门

### 3.1 `cmd/collector/acguard.go`（新增）

```go
var acProbes = []struct{ exe, label string }{
    {"PacNova", "完美平台 PacNova（Ring3 反作弊）"},
    {"PacNovaSvc", "完美平台 PacNova 服务"},
    {"wmpvp", "完美对战平台客户端"},
    {"wmpvp_anticheat", "完美对战平台反作弊"},
    {"5EClient", "5E 对战平台"}, {"5ECnClient", "5E 对战平台"},
    {"5EAntiCheat", "5E 反作弊"},
    {"FaceitClient", "Faceit 客户端"}, {"FACEITClient", "Faceit 客户端"},
    {"EasyAntiCheat", "EasyAntiCheat"}, {"EasyAntiCheat_EOS", "EasyAntiCheat (EOS)"},
    {"BEService", "BattlEye"},
    {"vgc", "Vanguard"}, {"vgtray", "Vanguard"},
}
```

- 只列**确定只在 AC 场景出现**的进程名，避免误伤（比如 `steam` 不能列）。
- `acBlockReason()` **只检测一次并缓存**：`resolvePID()` 在 hint 快路径里会被反复调用，
  每次遍历进程表要 5~15 ms，不缓存会把「握手 → 搜索」的延迟拖垮。
- `warnACBlocked()` 每次进程启动只打一次红字，把「为什么不出目标」写在用户面前。

### 3.2 闸门放在 `resolvePID()`

这是**所有内存访问的唯一入口**：

```
枚举区域     → resolvePID()
定位公钥     → resolvePID()
抓快照       → resolvePID()
找会话密钥   → resolvePID()
```

一处拦住 = 全拦住。而且闸门必须放在 `-pid` 判断**之前** —— 用户手动指定 PID
也不能绕过去（`TestResolvePIDIsGated` 钉的就是这个顺序）。

### 3.3 `-freeze` 默认改 `off`，新增 `-allow-ac`

| flag | 旧默认 | 新默认 | 说明 |
|---|---|---|---|
| `-freeze` | `short` | **`off`** | 不冻 = 不碰进程 |
| `-allow-ac` | 不存在 | **`false`** | 唯一逃生口 |

`-allow-ac` 的存在是必要的：如果完全没有逃生口，用户想在自己的社区服里跑
也会被误拦，最后会去改代码把闸门删掉 —— 那更危险。

## 七、必须对用户说清的三件事

1. **这轮改的不是解码，是安全。** 解码卡点（硬规则 210 那 655 字节容器层）没动。
2. **有反作弊的场次里，这一版安全但不出目标。**
   不碰进程 ⇒ 拿不到会话私钥 ⇒ 解不开包 ⇒ 雷达页没有目标。
3. **要出目标只有一条路：换纯社区服 + `-freeze short`。**
   `-allow-ac` 能强行恢复旧行为，但那正是 2026-10-19 封号那次的同一操作。
