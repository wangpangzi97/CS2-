## 二、三处假信号（已修）

### 假信号 1：`四个槽位命中线上四段 0/4` —— 其实找到了两段

现场落盘 `gns-kdf-20261019-150841.json` 里逐字节比对的结果：

```
conn+0x1798 指针目标 : 00 01 12 20 30327618 9d26bc7e …   ← server_cert
线上 server_cert     : 08 01 12 20 30327618 9d26bc7e …
                                  ↑ 除首字节外逐字节相同

conn+0x17b8 指针目标 : 00 01 12 20 02fcc7da 83b24e6a …   ← server_crypt
线上 server_crypt    : 08 01 12 20 02fcc7da 83b24e6a …
```

`02fcc7da83b24e6a…` 正是日志第 30 行记的**服务器临时公钥**，所以这条是硬证据。

**为什么会判 0/4：**
- `gnsMatchSlot` 拿**槽位自身那 16 字节**（`raw=00cd0c151b020000…`，一个指针）
  去和 97 字节的 cert 比 —— 位置就不对，永远不可能命中；
- 真正能命中的是 `gnsFindWireIn`（顺着指针读目标），但它取线上 blob 的
  **前 12 字节**当针，而内存里首字节是 `00`、线上是 `08` → 一个字节之差，全灭。

**修法**：新增 `gnsFindBlob(buf, data, probe)`，同时试「偏移 0」和「偏移 1」
两种针（偏移 1 命中后回退 1 才是 blob 真实起点）；`gnsScanRawForWire` 和
`gnsFindWireIn` 都改用它。`matchedCount` 也改成把 `PtrScan` 的命中算进去
（原来只数 `Matched`，而指针型槽位的命中根本不在 `Matched` 里）。

### 假信号 2：`判据帧 c2s=6 s2c=3` —— 恢复在开局第 1 秒就开跑了

```
[gnsmem] 判据帧 c2s=6 s2c=3（某个方向 <3 时那两组 IV 组合会被跳过）
[gnsmem] 内存恢复未命中（耗时 17.351s），判据帧 c2s=6 s2c=3
```

缓冲区上限是 `gnsMaxFrames = 24`，但闸门写的是：

```go
if len(c2s) < 6 && len(s2c) < 6 { return }   // 只要有**一边**到 6 就开跑
```

于是第一次恢复在 6/3 帧时启动。而 `gnsTryKey` 要求 **3 帧全部通过 GCM 认证**，
s2c 只有 3 帧 = 任何一帧不完整就把正确密钥判死，日志上只写「都不对」。
**这种假阴性比「没跑」难查得多。**

更糟的是 `gnsRecoverTries >= 3` 只给 3 次机会 —— 这 3 次全在开局几秒内烧完，
之后帧涨到 2000 也不再试。

**修法**：
- 闸门改成 `min(len(c2s), len(s2c)) < gnsRecoverMinFrames`（=6，即 3 帧要求的两倍）；
- 新增 `gnsRecoverAt`：帧数比上次多一档（+6）才重试，避免反复扫同一段内存；
- 重试上限 3 → `gnsRecoverMaxTries = 6`，覆盖 6/12/18/24 四档。

### 假信号 3：`快照耗时：201ms —— 全程在冻结窗口内` 紧接着 `冻结情况：未冻结`

```
[key] 快照耗时：201ms（4.32 GB/s｜4391 段｜短读 706）—— 全程在冻结窗口内
[key] 冻结情况：未冻结｜抓取 908664 KB｜**达到上限被截断**
```

`-freeze off` 分支根本不调 `freezeRun`，快照是在**进程照常运行**时抄的。
这句话正是用户判断「这局到底有没有碰进程」的依据，不能含糊。

**修法**：加 `snapFrozen` 标记，off 模式打
`—— **未冻结**，进程照常运行，这是活内存快照`。

## 四、仍然没解决的（诚实说明）

**密钥还是没拿到。** 内存里 conn±32KB 扫了 123700 个候选窗口（`[gnsnear]`），
CCrypto 那 4KB 里试了 205 个窗口，全没过 GCM 认证。

修复后的下一步会不一样，因为：
- 判据帧会从 6/3 变成 24/24（或至少 12/12），GCM 验证从「3 帧勉强」变成「24 帧充裕」；
- 如果之前是「判据帧不完整导致正确密钥被判死」，这次会命中；
- 如果还是不命中，那就基本可以确定**密钥不在 conn±32KB 里**，得换方向
  （例如顺着 CCrypto 指针再深挖一层，或者用 IV 高 4 字节去反查 KDF 变体）。

另外 `[gnskdf] salt 内存 [0x1890]=server_nonce [0x1968]=client_nonce` 这条判据是对的：
内存顺序是 `server||client`，与线上 `client||server` 相反，`需换 salt 顺序` 的结论保留。
