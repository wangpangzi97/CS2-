## 二、新卡点：netchan → netmessage 分帧，四种假设全否

我拿这局的两份产物做了四组独立测试，结果如下（脚本在 `2/work/gnsframe0{1,2,3,4}.py`）：

| # | 假设 | 结果 |
|---|---|---|
| 1 | `[u8 cmd][varint size]` 扫全流所有起点取最优链 | 最优起点 @34099 只走 **18 步 / 327 字节 = 0.3%**，随即断在 `b1 85 cd cd…` |
| 2 | 固定头部 0..9 字节 × 6 种长度字段（varint/u16/u24/u32），要求整包吃满 | **0/128 包**吃满 |
| 3 | 逐包扫**所有**起点，找吃满的链 | 20/128 报"吃满"，但全是 1~3 步的假命中（`cmd=63 size=64`、`cmd=0 size=73`），位置散落在包尾，不是真链 |
| 4 | 按位打包：`ReadUBitVar(cmd)` + varint(size)，LSB / MSB 各试 | cmd 出现 1505 / 57580 / 60136 这类值，**没有任何 svc_\* 聚集**（应集中在 4~80） |

补充一条关键旁证：`[snp] 首段位置=1` —— **流首字节缺失**，链的起点本来就不在偏移 0。

所以：`[u8 cmd][varint size]`（硬规则 207）在这条 netchan 流上**不成立**。
它当时是在 14:14 那批 msgFramed 上验证的，而那批本身还夹着 655 字节未识别容器块
（硬规则 210）。现在这两件事指向同一个结论：**SNP 的可靠消息拼接与 netmessage 之间
还隔着一层**。

## 三、这一轮改了什么

只有一处，但很关键 —— 把**带边界的**消息转储挂到更早的触发点上。

原来：
- `gns-netchan-*.bin` = 纯拼接，**边界被丢掉**（130476 字节里没法找边界）；
- `sess.msgFramed`（`u32le 长度 + 载荷`）确实在攒，但落盘阈值是 4000 条，
  这局只有 1285 条，**没到阈值就结束了**。

现在：netchan 攒到 64 KB 时，同时写出 `gns-msgframed-*.bin`（带 u32le 长度边界）。
下一局就能逐条对齐，直接回答「每条消息首字节是不是 01」「长度是不是第 2 字节 varint」
「尾部 protobuf 是否恒定」，不用再在拼接流里瞎扫。

```go
// internal/radarsrv/store.go
if !sess.netchanDump && len(sess.netchan) >= 64<<10 {
    ... 写 gns-netchan-*.bin ...
    if len(sess.msgFramed) > 0 {
        ... 写 gns-msgframed-*.bin（u32le 长度 + 载荷）...
    }
}
```
