# 16:27 分片头定案与样本截断

**一句话**：16:07 那批明文不是「128 条独立消息」，而是**一条连续流按 1137 字节切片**，
每片前面有 14 字节头，头里带绝对偏移。这层一定案，之前四轮「分帧假设全否」的
性质就变了 —— 那些否掉的是**切法**，不是**协议不存在**。

---

## 一、定案：GCM 明文 = 14 字节分片头 + 1137 字节载荷

16:07 的 128 条明文里，125 条长度完全一样 = 1151 字节，前 3 条是 54 / 28 / 98。
1151 那批的字节布局：

```
off  0  1  2  3  4  5  6  7 | 8..13        | 14..
    80 01 98 08 00 b4 00 57 | 1d 00 00 00 00 00 | 63 02 b0 35 03 ea ...
    80 02 98 08 00 b4 00 57 | 8e 04 00 00 00 00 | 44 3e 04 00 60 21 ...
    80 03 98 09 00 2c 00 57 | ff 08 00 00 00 00 | 40 40 33 00 00 50 ...
```

`off 8..13` 是个 6 字节小端数，相邻帧差值**恒等于 1137 = 1151 - 14**：

```
29 → 1166 → 2303 → 3440 → 4577 → 5714 → 6851 …  步长 1137
```

交叉验证（`gnsframe05.py`，125 条大帧，124 对相邻）：

| 头长 | 偏移字段位置 | 宽度 | 结果 |
|---|---|---|---|
| **14** | **8** | 4 / 5 / 6 字节 | **124/124 吻合** |
| 其他 4..24 的所有组合 | — | — | 全部不吻合 |

⇒ **头长 14 字节，偏移在 [8:12]，载荷从 14 开始，且载荷是连续流的切片。**
偏移基数 29 说明流的前 29 字节在抓包开始前已经过去了（中途开抓）。

前 3 条小帧（54/28/98）的头长度不同 —— 它们不是流分片，是控制消息。
判据：把 [8:12] 当偏移读，前两条得到 `0xFFFF00000001` 这种垃圾，第三条得到 1
（与 29 冲突），说明它们根本不是同一个头。

## 三、四连否：字节级 / 位级 / snappy / 其他压缩

流已经重建好了（剥 14 字节头、按 offset 排序、补空洞），142125 字节，空洞 56 字节。

### 3.1 字节级 `[u8 cmd][varint size][body]` —— 排除

`gnsframe12.py` 用 DP 求「从每个位置出发最长能连多少步」（O(n)，不受起点选择影响）：

```
最优起点 14041：62 步，吃掉 16719 / 142125 = 11.8%
已知锚点 6103：best=15 步
```

11.8% 是随机数据的水平（每次切一刀成功概率约 1/8，链长几十步）。
**真协议不可能只有 11.8%。**

### 3.2 位级 `ReadUBitVar + bitvarint` —— 排除

`gnsframe13.py` 把 DP 搬到**位**上（1137000 个位状态），四种组合：

| 顺序 | size 单位 | 最长链 | 覆盖 | cmd 取值 |
|---|---|---|---|---|
| lsb | 字节 | 40 步 | 71.4% | 出现 `114004095` |
| lsb | 位 | 49 步 | 10.2% | 出现 `2900858012` |
| msb | 字节 | 40 步 | 36.9% | 出现 `951269546` |
| msb | 位 | 47 步 | 6.0% | 出现 `4099` |

覆盖率看着不低，但**cmd 出现 10 位数**——真 cmd 不可能超过 255。
lsb/字节那组 71.4% 是靠一个 `cmd=3734646896 size=100` 的巨型跳过凑出来的，
是伪覆盖。排除。

### 3.3 snappy —— 排除

线索本来很像：整体熵 7.96，但里面嵌着**字节对齐的原始 protobuf**，
这正是 snappy 字面量块的表现。而且把 `0x54` 当 snappy 标签解，
`(0x54>>2)+1 = 22` 字节，正好落在 `... 28 00` 之后、`30 00` 之前。

`gnsframe14.py` 写了完整的 snappy block 解码器，判据是四条全过：
声明长度 varint 合法 / 所有 tag 合法 / **输入精确吃完** / **输出精确等于声明长度**。

```
每条载荷当独立块 : 精确命中 0/125
整条流当一块     : 声明长度 99，解压失败
全流每个偏移试起点: 0 命中
```

排除。

### 3.4 zstd / lz4 / xz / bzip2 / gzip —— 魔数全无

```
zstd(28b52ffd) 未出现   lz4(04224d18) 未出现   xz 未出现   bzip2 未出现
gzip 出现在 67764、zlib 出现在 95207 —— 都在高熵区，是随机巧合
```

## 四、三条 cmd=39 消息是真的（新锚点）

全流 `54 00 27` 只出现 **3 次**，正好对应三条带名字的 protobuf：

| 位置 | 头 | 名字 | size | protobuf 校验 |
|---|---|---|---|---|
| 6103 | `54 00 27` | `userinfo` | 816 | ✅ fields=10 |
| 7540 | `54 00 27` | `VguiScreen` | 28 | ✅ fields=9 |
| 7898 | `54 00 27` | `AnimAssetData` | 16621 | ❌ 尾部不完整 |

前两条通过「protobuf 必须恰好吃完」的强判据，字节级证据：

```
6106: 0a 08 "userinfo" 10 40 18 00 20 00 28 00 30 00 3a 92 06 <786 字节嵌套>
7542: 0a 0a "VguiScreen" 10 00 18 00 20 00 28 00 30 00 ...
```

`0x27 = 39`，与 14:50 定案的 cmd=39 一致。**这是协议真实存在的硬证据**，
也是唯一能把「分帧」和「随机数据」区分开的锚点。

第三条 `AnimAssetData` size=16621，体从 7902 到 24523。**这个数和熵图对得上**：

```
滑动熵（窗口 256）：
      0  4.729   ← signon 起点，结构最密
   6144  5.963
  20480  6.396
  22016  5.523
  22528  4.765   ← 又一个结构化谷底
  24576  6.351
  25088  7.130   ← 跳上来，进局
  29696  7.243
```

熵在 24576→25088 之间从 6.35 跳到 7.13。16621 那条消息结束在 24523，
**正好卡在这个跳变之前**。⇒ size=16621 是对的，signon 段到 24523 结束，
之后是进局的实体数据（熵 7.1~7.2，位打包/压缩特征）。

**所以：signon 段有 3 条 cmd=39 消息可锚定，但它们之间和之后的字节
用现有任何切法都接不上。** 这就是当前卡点的精确形状。

## 五、本轮真正的工程失误：样本被截断了

这一局 `[dec] 已解帧=3251`，但 `gns-plain-*.json` 里只有 **128 条**。
原因：

```go
const plainDumpTarget = 128   // 攒够 128 条就落盘，然后 plainDone=true 再也不落
```

128 条 × 1151 ≈ 142 KB，只够 signon 前段。**进局后的 3000 多条实体消息
一条都没留下来。** 而我拿这 142 KB 去判断「封装是什么」，样本本身就缺了
整个对局段 —— 这也是为什么 3.2 里 lsb/字节那组会「看起来 71.4%」。

### 改法（`internal/radarsrv/store.go`）

1. `plainDumpTarget` **128 → 512**（约 570 KB，覆盖到开打之后）；
2. 新增 `savePlainBin`：s2c 明文**全量**收，`[u32le len][bytes]` 落二进制
   （`gns-plainbin-*.bin`），每 4096 帧一份，一局最多 3 份（约 20 MB 上限）；
3. 新增 `gnsRebuildStream`：落盘时**直接把干净流重建出来**
   （`gns-stream-*.bin`）—— 剥 14 字节头、按 offset 排序、空洞补零，
   离线不用再猜一遍。日志会打一行：
   ```
   [room1] 干净流：N 帧分片（头 14 字节）→ M 字节流，空洞 K 字节
   ```

新增测试 `internal/radarsrv/store_stream_test.go`（5 条，全绿）：

- `TestGNSRebuildStreamStripsHeaderAndOrders` — 剥头 + 按 offset 排序
- `TestGNSRebuildStreamIgnoresMinorityLength` — 小帧不能混进流
- `TestGNSRebuildStreamFillsHole` — 空洞补零，不能硬拼
- `TestGNSRebuildStreamRejectsSingleFrame` — 样本太少宁可返回空
- `TestPlainDumpTargetCoversIngame` — 盯住样本上限不许再退回 128

写测试时当场抓到两个真 bug：帧计数少算第一片；小帧长度与众数相同会混进来。

## 六、下一轮要什么

**要一份 `gns-stream-*.bin`，3.7 MB 左右（不是 142 KB）。**

判据看这两行：

```
[room1] 已把 4096 条解密明文（累计 N 条，X 字节）写到 …\gns-plainbin-….bin
[room1] 干净流：4096 帧分片（头 14 字节）→ 4657152 字节流，空洞 0 字节
```

- **空洞必须是 0** —— 不是 0 说明有丢帧，流是断的，那一切分帧都会失败；
- 流长度应该在 3.7 MB 上下（3251 帧 × 1151）。

拿到之后第一件事：在**完整流**上重跑 `gnsframe12.py` 的 DP。
如果 142 KB 上 11.8%，3.7 MB 上还是 11% 左右，说明 `[cmd][size]` 彻底死了；
如果跳到 90%+，那就是样本太短导致的假阴性。

## 七、结论

1. **分片头定案**：14 字节头 + 1137 字节载荷，offset 连续（124/124 帧）。
   128 条明文是**一条流**，不是 128 条消息。
2. **四连否**：字节级 DP 11.8%、位级 DP 出 10 位 cmd、snappy 0/125、
   压缩魔数全无。都不是。
3. **三条 cmd=39 锚点是真的**，`AnimAssetData` 的 16621 与熵图跳变吻合，
   signon 段结束在 24523。
4. **本轮最大失误是样本截断**：3251 帧只落 128 条，进局段全丢。已修，
   并且把流重建搬到采集端。
5. 密钥链路不受影响 —— 16:07 那次的 `has_key=true`、16/16 + 64/64 GCM 仍然成立。
   卡点仍然是**唯一一处**：分片流内部的消息分帧。
