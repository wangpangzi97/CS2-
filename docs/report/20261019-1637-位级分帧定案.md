# 16:37 位级分帧定案 —— 卡了两天的内层封装解开了

**一句话**：netmessage 一直就在那里，之前四轮「分帧假设全否」全是因为**分析对象错了**。
我一直在把「多条可靠消息首尾相接」的流里找边界，而边界本来就是**可靠消息自己的边界**。

---

## 一、根因：分析对象错了一层

| 层级 | 单位 | 之前怎么做的 | 对的 |
|---|---|---|---|
| UDP 包 | GCM 明文帧 | 有 14 字节分片头（硬规则 219，那是对的） | ✅ 没错 |
| **SNP 可靠消息** | **一条 = 一段 netmessage 链** | **把它们拼成一条流再找边界** | ❌ **这里错了** |
| netmessage | 位打包 | 在拼接流上按字节/位扫 | 边界在上一层，白扫 |

`gns-msgframed-*.bin` 从 16:07 那轮就已经在落了（`u32le 长度 + 载荷`），
但我一直把它当成「拼流的原料」，没意识到**它本身就是边界**。

---

## 二、定案：一条可靠消息 = `01` + varint(tick) + 位打包链

```
[u8 0x01][varint tick][位打包的 netmessage 链]

链里每条：
  cmd  = ReadUBitVar()   ← Source 版，不是「2 位选择器」简化版
  size = ReadVarInt32()  ← 每次 8 位，低 7 位数据、最高位续读，最多 5 组
  body = size 个字节，从当前**位**位置开始（不字节对齐，必须逐位取）
```

### 2.1 ReadUBitVar 必须是 Source 版

```c
int ReadUBitVar() {
    int ret = ReadUBitLong(6);          // 先读 6 位
    switch (ret & 0x30) {               // 看的是这 6 位里的第 4、5 位
        case 0x10: ret = (ret & 15) | (ReadUBitLong(4)  << 4); break;
        case 0x20: ret = (ret & 15) | (ReadUBitLong(8)  << 4); break;
        case 0x30: ret = (ret & 15) | (ReadUBitLong(28) << 4); break;
    }
    return ret;
}
```

**硬规则 218 第 4 组失败的直接原因就是用了简化版**（先读 2 位当选择器），
于是读出 1505 / 57580 / 60136 这类垃圾 cmd。真实数据里 `1f 13` 就是 cmd=207：

```
0x1f 前 6 位 = 31 → 31 & 0x30 = 0x10 → 走「再读 4 位」档
再读 4 位 = 12
cmd = (31 & 15) | (12 << 4) = 15 | 192 = 207
```

### 2.2 位序是 LSB-first

每个字节内从最低位开始。MSB-first 一组 0 命中。

## 四、采集端那个 bug：`feedMsg` 把整条载荷当一个 protobuf

```go
// 旧代码
if ents, err := handshake.ParsePB(payload); err != nil || len(ents) == 0 {
    sess.msgBitpacked++      // ← 322 条全落到这里
    return
}
```

`ParsePB` 是**严格**的（必须一个字节不剩地解析完）。而载荷是位打包的多条消息，
所以 322 条里 0 条满足 —— 全部计入「位打包」，`消息=0 玩家=0` 就是这么来的。

**修复**（`internal/radarsrv/gnsbitmsg.go` 新增，`store.go` 的 `feedMsg` 改造）：

1. 新增 `gnsBitReader`（LSB-first 位读取器）+ `readUBitVar`（Source 版）+ `readVarInt32`；
2. 新增 `gnsParseNetMsgs(m)`：拆出 `[]gnsNetMsg{Cmd, Body, HdrBits}` 和 tick；
3. `feedMsg` 改成：先走位级拆分 → 逐条 body 判 protobuf → 逐条 `dec.Feed`，
   **`Cmd` 用真实的 cmd**（旧代码错把 `flags` 当 cmd）；
4. 保留兜底：首字节不是 `0x01` 的载荷回退到「整条当一个 protobuf」
   （现场 6/328 条 + 测试夹具走这条路）；
5. `logNetMsgFrames` 重写：从「拼流扫起点」改成「逐条校验精确吃满」。

新增日志：

```
[gnsmsg] 位级分帧：N 条 netmessage（来自 M 条可靠消息）｜cmd 种类=K｜前10 ...
[gnsmsg] body 当 protobuf 喂进解码器 X 条｜首字节非 0x01 跳过 Y 条
[net] 位级分帧校验：328 条可靠消息｜精确吃满 322｜未吃满 0｜不是 netmessage 链 6
[net] cmd 种类=10｜前10 207×591 208×150 ...
```

**`[net] 精确吃满` 这一行是新的主指标。** 现场应当看到
`精确吃满 ≈ 总条数 - 6`；如果 `未吃满` 很大，说明还有别的帧类型混进来。

## 六、还没解决的：这些消息里没有实体

这一局解出来的 840 条 netmessage 里：

- **cmd=207（591 条）** 是完美平台的 UI 更新（剩余时间 / 急停成功率 / logo）；
- **cmd=201（73 条）** 带 float 三元组，但值是 `(1674.8, 0, 0)`、`(0.5, 0, -0)` 这种
  —— y/z 恒为 0，是**角度/向量**，不是世界坐标（`svc_SetView`/`svc_Sounds` 一类）；
- **cmd=58（1 条）** 是 `CNETMsg_SetConVar`。

840 条里含合理 float 三元组的只有 55 条，且全是 cmd=201 的角度值。
**没有 `svc_PacketEntities` 的迹象。**

判断：这一局（16:29:46~16:30:42，96 秒）大概率**不在实际对局里**，
或者刚进服还没开始。完美平台的 UI 流量把带宽占满了。

## 七、下一轮要什么

**在对局里跑一局**（真正打起来），然后看这两行：

```
[net] 位级分帧校验：N 条可靠消息｜精确吃满 N-6｜未吃满 0｜不是 netmessage 链 6
[gnsmsg] 位级分帧：M 条 netmessage｜cmd 种类=K｜前10 ...
```

判据：

1. **`未吃满` 必须接近 0** —— 大就说明还有别的帧类型没处理；
2. **cmd 种类应当收敛**（这一局 10 种）。如果冒出上百种，说明位序或 ReadUBitVar 又错了；
3. **cmd 分布里要出现大 size 的消息**（实体快照通常几百到上千字节，且高频）。
   这一局 207 占 591 条但都是 UI，size 324 固定 —— 一看就不是实体。

有了对局样本，下一步是：按 cmd 分类 → 找出哪一个是实体快照 →
再解决 delta 编码（需要 baseline，硬规则 190/191）。

## 八、结论

1. **内层封装定案**：`01` + varint(tick) + 位打包链，`ReadUBitVar`(Source 版) + `ReadVarInt32`。
2. **验证**：322/322 精确吃满、cmd 只有 10 种、body 185/196 是合法 protobuf。
3. **根因**：不是协议难，是我把「边界已知的消息」拼成了「边界未知的流」。
   `gns-msgframed` 从 16:07 就在落了，我没当边界用。
4. **采集端已修**：`feedMsg` 不再要求「整条载荷是一个 protobuf」。
   `消息=0` 的直接原因就在这里。
5. **仍未解决**：这一局没有实体数据（不在对局内）。需要一份真正对局的样本。
