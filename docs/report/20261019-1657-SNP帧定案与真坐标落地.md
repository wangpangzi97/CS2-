## 二、14 字节「分片头」的真相

前几轮（硬规则 219）把每帧明文的前 14 字节当成「分片头」，靠暴力搜索得出
「hdr=14、offset@8、stride=1137」。数值是对的，**语义全错**。

真相在 `GameNetworkingSockets` 的 `src/steamnetworkingsockets/clientlib/SNP_WIRE_FORMAT.md`：

```
80 01                    ← 帧1  100000ww   stop waiting (8-bit offset = 1)
98 08 00 b4 00           ← 帧2  1001wnnn   ack (w=1 → 16bit pkt_num=8, delay=180)
57                       ← 帧3  010mmsss   可靠段: mm=10 → 48位流位置, sss=111 → 数据到包尾
1d 00 00 00 00 00        ← 48 位 stream_pos = 29
<1137 字节>              ← 1137 = 1151 - 14
```

所以 14 = 2（stop waiting）+ 5（ack）+ 1（可靠段首字节）+ 6（48 位流位置）。
`stride = 1137` 是必然结果，不是巧合。

### 1232 那类为什么「无解」

`[7] = 0x51` → `sss = 001` → **size = 0x100 + 显式字节**，`0x100 + 0x4d = 333`。
所以一个包里有多段，stream_pos 只覆盖第一段，按整帧长度求 stride 当然无解。
现场按 offset 排序的差值分布 `333×106 / 334×101` 就是这个 333/334。

`[7] = 0x1f` → `00 e m o sss` → **不可靠消息段**，也就是之前一直丢掉的那部分。

### 帧类型对照（官方）

| 首字节 | 类型 | 载荷 |
|---|---|---|
| `00 e m o sss` | 不可靠消息段 | msg_num + offset + size + data |
| `010 m m sss` | 可靠流段 | stream_pos（24/32/48 位或相对偏移）+ size + data |
| `100000 ww` | stop waiting | 8/16/24/64 位 offset |
| `1001 w nnn` | ack | 16/32 位包号 + delay + nnn 个块 |
| `10001 nnn` | 选通道 | lane 号 |

`sss = 7` 表示「数据延续到包尾」，`sss = 0..4` 表示 `size = (sss<<8) | 下一字节`。

## 三、cmd=208 就是位置消息（硬规则 225）

那一局在真正对局内，9256 条 netmessage 里 cmd=208 出现 1722 次。protobuf 结构固定：

```
field 1  varint   —— 全局消息序号（每条 +1，现场 28228 起）
field 2  fixed32  —— 不是坐标（打包的位域）
field 3  varint   —— 实体索引（现场 66..511，并发中位 61）
field 4  varint   —— 与 field 1 相同
field 5  bytes    —— 30 字节定长 blob，坐标在里面
```

blob 布局（1709/1722 条如此）：

```
[0..3]   4d ce 7c 5a      4 字节常量
[4..5]   0a 0c            位置标记（判据）
[6]      00               常量
[7..18]  x, y, z          三个 float32 小端 ← 世界坐标
[19..21] 41 e1 1b         多数恒定
[22..25] d9 02 04 00      恒定
[26..29] 4 字节           18 种取值
```

### 为什么确信是真坐标

`tag3 = 238` 的 148 个采样点按到达序连起来：

```
(-2014.56, -457.68, -167.97)
(-1938.10, -499.07, -167.97)
(-1865.88, -528.29, -167.97)
(-1861.94, -529.78, -167.97)
(-1750.00, -674.15, -163.78)
(-1747.91, -677.59, -167.94)
```

每一步 50~80 单位，z 稳定在 -167.97（地面高度），是**人在跑**。
`tag3 = 366` 的轨迹也平滑，末点 `z = -366.20`（跳下/坠落）。

采样数呈明显断层：`148, 124, 120, 118, 102, 100, 92, 90, 89, 81, 74, 63 | 34, 32, 31...`
——前 13 个是活跃实体（玩家），后面是零星道具。

### 三条采信判据

1. `blob[4]==0x0a && blob[5]==0x0c`（位置标记）；
2. 三个 float 都有限且 `|v| < 20000`（CS2 地图量级）；
3. x、y 不同时接近 0（过滤空槽位的零值）。

按这三条在 1722 条上跑，**命中 1722/1722 = 100%**。

## 五、不可靠消息：拿到了，格式未定（硬规则 226）

```
段数 3819 → 3042 条消息，全部完整（3042/3042）
长度 P10=379 中位=569 P90=1320 P99=2051 max=3001
首字节分布： 0x02 ×2630 | 0x04 ×410 | 0xff ×2
```

四种内层假设全部否掉：

| 假设 | 结果 |
|---|---|
| H1 `flags + varint(tick) + 位打包链`（与可靠消息同一套） | 0.3% / 0.2% |
| H2 `flags + varint(size)` | 0/2630、0/410 |
| H3 `cmd + varint(size)` 字节对齐 | 0/3042 |
| H4 `flags + u16le(size)` | 1/3042 |

**但拿到了两个强线索**：

1. 最长几条里有一段反复出现的固定字节：
   `18 00 1a c0 35 ?? ?? 08 80 04 10 20 18 01 20 00 28 00 30 ?? ?? 04 3a ?? ??`
   这种「同位置同值」只可能是 protobuf 的固定字段区，不是随机位打包。
2. 首字节只有 `0x02 / 0x04` 两种（`0xff` 那 2 条是 SDR 无连接控制包，
   内容是 `ff ff ff ff 41 ... "connect0"`）。

下一步只需要一份 `gns-unrel-*.bin` + 对局内的时间对齐，就能定案。

## 六、代码改动

### 新增 `internal/radarsrv/gnspos.go`

- `gnsParsePosMsg(body) (ent, pos, ok)` —— cmd=208 的专用解析：
  protobuf 字段遍历取 field3/field5，再按定案布局取 xyz，三条判据缺一不可。
- `Session.noteGNSPlayerPos` —— 记「实体 → 最新位置」，带 1024 上限与过期清理。
- `Session.gnsPlayerSnapshot(now)` —— 只返回 `gnsPosTTL = 6s` 内更新过的条目，
  按实体索引升序（保证画面稳定，map 遍历顺序是随机的）。
- `gnsTopBytes` / `gnsTopLens` —— 日志用的直方图格式化。

### 改 `internal/radarsrv/store.go`

1. **不可靠消息不再丢弃**：新增 `unrelDump/unrelCount/unrelHead`，
   按 `u32le 长度 + 载荷` 攒，满 2 MB 落一份 `gns-unrel-*.bin`，
   落盘时打首字节分布 + 长度分布。
2. **`feedMsg` 里 cmd=208 走专用解析**：命中就 `noteGNSPlayerPos` 并 `continue`，
   不再交给启发式扫 float3（启发式会同时扫出 tag2 位域和 blob 尾部垃圾浮点）。
3. **`Snapshot` 改成两条来源、真坐标优先**：
   ```go
   players := sess.gnsPlayerSnapshot(time.Now())
   if len(players) == 0 {
       players = sess.decoder.Snapshot()
   }
   ```
   原来只有启发式那一条，现场就是 `玩家=64 最佳=无` —— 数字是扫出来的，位置全是垃圾。
   现在只要真坐标有货就**完全不用**启发式：在真坐标旁边混进几十个幽灵，比画面空着更糟。
4. **新增 `[gnspos]` 日志**：`cmd=208 解出坐标 P 条｜当前实体 E 个｜平均采样 P/E`。
   `E` 就是对局里画出来的目标数，正常在 10 上下。

## 八、下一局怎么看

跑一局**真正打起来**的，然后看这四行：

```
[net] 位级分帧校验：N 条可靠消息｜精确吃满 X｜未吃满 Y｜不是 netmessage 链 Z
[gnsmsg] 位级分帧：M 条 netmessage｜cmd 种类=K｜前10 ...
[gnspos] cmd=208 解出坐标 P 条｜当前实体 E 个｜平均采样 P/E
[unrel] 共 N 条｜首字节（前6）...｜长度（前6）...
```

判据：

1. **`未吃满` 必须是 0**（这一局是 0）；
2. **`cmd 种类` 应收敛**（这一局 19 种）。冒出上百种说明位序或 ReadUBitVar 又错了；
3. **`[gnspos] 当前实体 E` 应当在 10 上下** —— 这是雷达真正画出来的目标数。
   如果 E = 0 但 `[gnsmsg] cmd` 里 208 有几千条，说明 blob 布局又变了；
4. **`[unrel]` 的首字节分布**决定下一步能不能定案不可靠通道的格式。

## 九、残留风险

1. **cmd=208 的频率只有约 1.7 Hz/实体**（1722 条 ÷ 77 秒 ÷ 13 个实体）。
   这个频率画出来会「一跳一跳」，不是平滑移动。真正的高码率实体流应当在
   不可靠通道里 —— 也就是还没解开的那 3042 条。
2. **实体索引 66..511 的语义未定**。CS2 玩家实体通常是低索引，
   这里 66 起跳，可能是另一种索引空间（chunk 内偏移）。不影响画面，但影响
   「谁是敌人、谁是队友」的判定 —— 现在**没有队伍信息**。
3. **tag2 的 fixed32 还没解**（值像位域，不是浮点）。
4. **`gns-unrel-*.bin` 只留了 2 MB 一批**，长对局会覆盖多份文件，注意别只取最新那份。
