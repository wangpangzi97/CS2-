## 二、证据链

### 2.1 白名单丢了 75439 个像 GNS 的包

```
[stats] 收 102181 包｜过滤丢弃 96598（其中像 GNS 的 75439）（白名单 41 个端口）
        ｜c2s 87244 s2c 14937｜最忙端口 51596(96595) 47960(96542) 17002(5332) 63976(5317)
[cap] ⚠ 白名单丢掉 75400 个像 GNS 的包（51596→47960，1143 字节）
```

- 102181 个包里 96598 被丢，其中 **75439 个首字节高位为 1**（GNS 密文帧特征）。
- 这些包的载荷长度 1104~1180 字节，与已定案的「14 字节 SNP 帧头 + 1137 字节载荷 = 1151」
  是同一类；扣掉帧头就是 1090~1166，正是可靠段的典型大小。
- 白名单只有 41 个端口，全部在 `60898..60968` 区间（`cs2.exe` 自己的 socket）。
  **51596 / 47960 一个都不在里面。**

为什么白名单漏了：`Discover()` 走 `GetExtendedUdpTable` 只取 `cs2.exe` 名下的端口。
真正的链路跑在**平台中转 / 加速器持有的端口**上，不是 cs2.exe 的 socket，于是全丢。

之前只在丢包时打一行「signon 可能正被丢弃」，**从来不管**。这是这一局的直接原因。

### 2.2 一个洞把整条 s2c 流锁死

```
[snp] 方向=s2c 包=139  可靠段=133  可靠消息=34 流位置=146526 已出=146525 最大空洞=0
[snp] 方向=s2c 包=468  可靠段=337  可靠消息=34 流位置=149309 已出=149308 最大空洞=101969 待补段=201
[snp] 方向=s2c 包=802  可靠段=542  可靠消息=34 流位置=149309 已出=149308 最大空洞=180394 待补段=406
[snp] 方向=s2c 包=1107 可靠段=748  可靠消息=34 流位置=149309 已出=149308 最大空洞=260652 待补段=612
[snp] 方向=s2c 包=2073 可靠段=1350 可靠消息=34 流位置=149309 已出=149308 最大空洞=497159 待补段=1214
```

从第二条统计开始：`流位置` 恒定 149309、`可靠消息` 恒定 34，而 `可靠段` 从 133 涨到 1350。
也就是说**后面 1200 多个段全都堆在 pending 里等**，因为 149309 那个位置永远补不上。

`cs2snp.Stream` 原来的语义是「必须位置连续才交出去」—— 这在设计上是对的
（乱序拼接错一位就全错），但**没有出口**：洞一旦补不上，流就永久卡死。
一个包丢掉 = 一局白打。

### 2.3 卡死的连带后果

`netchan=7096 已切=7083` 也是从第二条统计起恒定。所以：

- `消息=1`（只有兜底路径那一条）
- 没有 `[net] 位级分帧校验`（`msgCount=0`，`logMsgStats` 不触发）
- 没有 `[gnspos]`（没有 cmd=208 进来）
- 玩家 0

### 2.4 顺带查到的浪费

```
[gnsnear] 锚点 9 个 / 扫 330.2 KB / 试 176132 个窗口，都没通过 GCM 认证（耗时 16.005s）
[gnsmem] 0x1bf3c7f8fe0 起 4096 字节内试了 177 个候选窗口，都不对   ← 刷了 6 遍
```

这些发生在 `[room1] GNS 复核：16/16 帧 GCM 认证通过` **之后**。密钥已经拿到了，
内存恢复还在反复遍历 cs2.exe 的内存。对局中白烧 CPU 和内存带宽，对结果零影响。

## 三、改动

### 3.1 `capturefilter.AutoAdmit`：白名单漏了就自己补（`internal/capturefilter/filter.go`）

```go
const autoAdmitMax = 12

// AutoAdmit 在「已经看到一个像 GNS 加密帧的包、但两个端口都不在白名单里」时，
// 把这对端口并进白名单。返回真正新增的端口。
func (f *Filter) AutoAdmit(a, b uint16) []uint16
```

- 过滤未生效（`len(ports)==0`）时**直接返回 nil**，绝不把「全收」变成「只收两个端口」。
  这是 `Discover` 失败时的兜底路径，不能破坏。
- 上限 12 个端口，防止退化成全收。
- `Set()` 重置计数，`AddPort()`（握手那条路）不计入自动配额。

### 3.2 丢包点：从「只打日志」改成「直接放行」（`cmd/collector/main.go`）

判据收紧到 **首字节高位为 1 且长度 ≥64**（普通应用几乎不发这种载荷）：

```go
if len(udp.Data) >= 64 && udp.Data[0]&0x80 != 0 {
    n := atomic.AddUint64(&s.filterDropGNS, 1)
    added := s.cfilter.AutoAdmit(udp.SrcPort, udp.DstPort)
    s.noteDropFlow(udp)
    if len(added) > 0 {
        // [cap] ⚠ 白名单漏了 GNS 端口，已自动放行 [51596 47960]（ip:port → ip:port，1143 字节）
        ...
    }
    if !s.cfilter.Match(udp.SrcPort, udp.DstPort) {
        continue
    }
    // 刚放行的这条流，本包也按正常路径处理下去
}
```

### 3.3 `[stats]` 带上被丢流的完整五元组

```
[stats] ...｜最忙端口 51596(96595) ...｜被丢的GNS流 172.17.122.10:51596→1.2.3.4:47960×75400
```

原来只打端口号，没有 IP，**根本判断不出那条流是游戏主链路还是本机回环**。
现在 `dropFlow` 表记前 64 条不同五元组的次数，`topDropFlows(4)` 取前 4 条。
下一局一眼就能定性。

### 3.4 `cs2snp.Stream.SkipStale`：空洞兜底（`internal/cs2snp/stream.go`）

```go
const (
    holeMaxAge     = 5 * time.Second  // 洞等 5 秒还没来，基本断定永远抓不到
    holeMaxPending = 512              // pending 堆过 512 段，流已经死了
)

// SkipStale 在「空洞等太久或堆太多」时强行跳过，返回跳过的字节数和是否跳了。
func (s *Stream) SkipStale(now time.Time) (int64, bool)
```

- 两条判据都要有：只看时间不够（s2c 每秒几十个段，512 段十几秒就堆满），
  只看数量也不够（慢速流永远堆不到）。
- 跳过后 `next` 直接落到 pending 里最小的位置，`drainPending()` 把连续的那截一次吐出。
- 调用方（`store.go`）在跳过后**必须 `msgSplit.Reset()`**：新位置不是消息边界，
  要让它从新位置重新按消息头同步。`MsgSplit.Feed` 本来就有逐字节重同步路径。

权衡：不跳 = 整条流永久卡死（实测整局作废）；跳 = 丢一小段、可能混进几条乱消息。
后者明显更好 —— 而且 `feedMsg` 会按「首字节 01 + 位级精确吃满」把乱消息挡掉，
不会画出幽灵目标。

### 3.5 `[snp]` 日志新增「跳过」字段

```
[snp] 方向=s2c 包=N 可靠段=N ... 待补段=N 跳过=3次/412233字节 netchan=N 已切=N
```

`跳过` 非零就说明**抓包漏了包**（SNP 自己会重传，等 5 秒还补不上只能是抓包链路丢的）。

### 3.6 `maybeRecoverGNS` 提前退出（`cmd/collector/gnskey.go`）

```go
if s.keyReady.Load() && !*flagMemSessionKey {
    return
}
```

密钥已经通过 GCM 认证并交给解析器之后，内存恢复没有任何意义。`-mem-session-key`
仍然可以强制开启（排障用）。

## 六、下一局看什么

按重要性排序，只看这四行：

```
[cap] ⚠ 白名单漏了 GNS 端口，已自动放行 [...]（ip:port → ip:port，1143 字节）
[stats] ...｜被丢的GNS流 ip:port→ip:port×N
[snp] 方向=s2c ... 可靠消息=N 流位置=N 跳过=K次/M字节 ...
[gnspos] cmd=208 解出坐标 P 条｜当前实体 E 个
```

判据：

1. **`被丢的GNS流` 应该只剩很小的数**（自动放行生效）。如果还在几十万量级，
   说明放行没起作用 —— 把那一行原文发出来。
2. **`跳过=0次`** 是理想值。非零说明还有丢包，但至少流不会再卡死。
3. **`可靠消息` 必须持续增长**。恒定不动就是还有别的洞在锁流（这时 `跳过` 会同时涨）。
4. **`E` 就是对局里画出来的目标数**，正常 10 上下。

⚠ 已知短板（和上一轮一致，本轮没动）：cmd=208 约 1.7 Hz/实体，画面会一跳一跳；
实体索引 66..511 语义未定；**没有队伍信息，分不出敌我**。
