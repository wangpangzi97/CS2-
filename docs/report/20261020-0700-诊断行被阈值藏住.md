## 二、真正的问题：三个诊断行一条都没打出来

全日志 `grep -E "\[(net|gnsmsg|gnspos)\]"` → **零命中**。

原因在代码里：

```go
// store.go，logMsgStats 的末尾
if sess.msgCount >= sess.msgDumpAt+msgDumpEvery {   // msgDumpEvery = 4000
    ...
    sess.logMsgStats()      // ← [gnsmsg] / [net] / [gnspos] 全在这个函数里
}
```

`logMsgStats` 只在**可靠消息累计满 4000 条**时触发一次。这局跑了 70 秒、
3297 条，**永远到不了 4000**，于是：

- `[gnsmsg]`（cmd 分布）没打；
- `[net]`（吃满率）没打；
- `[gnspos]`（**当前实体 N 个** —— 雷达真正画出来的目标数）没打。

这不是「没解出东西」，是「解出来了但没吭声」。

### 一个被误读两轮的数字

`[dec] ... 玩家=64 最佳=无` —— 我一直按「64 是启发式的上限」解释，判成「全是垃圾」。
但对照整局：

```
[dec] 已解帧=8117 消息=5493 玩家=64
[dec] 已解帧=8963 消息=6182 玩家=63
[dec] 已解帧=9707 消息=6908 玩家=61
[dec] 已解帧=10713 消息=7606 玩家=63
```

**64 → 63 → 61 → 63 是变的。** `HeuristicDecoder.Snapshot()` 里没有任何 64 上限
（`internal/cs2proto/entity.go:164`，就是按 TTL 过滤一遍），所以 64 不是饱和值，
是一个真实波动的条目数。

而 `Session.Snapshot()` 的逻辑是「`gnsPlayerSnapshot()` 有货就完全不用启发式」。
结合 `gns-msgframed` 里 cmd=208 占 10/48 且 **10/10 都能解出坐标**（下面第三节），
最可能的真相是：**这局一直在用真坐标画 60 来个目标**，只是没有任何一行日志能证明。

## 四、不可靠通道：第 5 次否定，且这次是机器扫的

上一轮四种人肉假设全否。这轮改成**参数全扫**，维度：
起始字节偏移 0..12 × 位序 LSB/MSB × cmd 编码（ReadUBitVar / varint32 / 6 位定长）
× size 编码（varint32 / u16le / u16be），共 13×2×3×3 = 234 种组合，
对四个最大的定长类各跑 60 条，判据「解析完剩余位 < 16」。

最高命中率 **3%**（2/60），次高 2% —— **全部随机水平**。

不可靠消息的画像（4598 条 / 2.75 MB）：

```
(首字节,长度) top:  0x04/879 ×155   0x02/879 ×135   0x04/882 ×131   0x02/882 ×91
首字节分布:        0x02 ×2713  0x04 ×614  0x00 ×116  0x01 ×65  0x03 ×34 ...
```

对 `0x04/len=879` 做恒定字节分析：**879 个位置里只有 2 个恒定**（`[0]=04`、`[6]=00`）。
不是字节对齐的结构体，也不是 protobuf（protobuf 的字段号会给出大量恒定 tag 字节）。

**结论：不可靠通道不是「netmessage 链」，也不是任何字节对齐的容器。**
下一步要换思路（候选：位打包的 delta 快照、或先按 msg_num/offset 重组分片）。

## 五、本轮改动

### 1. 诊断三行挂到 3 秒节拍上（`store.go`）

新增 `logGNSDecodeStats()`，把 `[gnsmsg]` / `[net]` / `[gnspos]` 从
`logMsgStats` 里抽出来，在 `logDir` 的 3 秒节拍上调用（只在 s2c 侧调一次）：

```go
func (sess *Session) logGNSDecodeStats() {
    if sess.gnsStatAt != (time.Time{}) && time.Since(sess.gnsStatAt) < 3*time.Second {
        return
    }
    sess.gnsStatAt = time.Now()
    if sess.gnsMsgTotal > 0 { ... [gnsmsg] ... } else { ... "还没有解出任何 netmessage" ... }
    sess.logNetMsgFrames()
    sess.logGNSPosStats()
}
```

`[gnspos]` 特意**不走** `logNetMsgFrames`：那边开头有
`if len(sess.msgFramed) == 0 { return }`，而 `msgFramed` 每 4000 条落盘后会清空，
坐标统计就再也打不出来。

### 2. `[gnspos]` 加三个新维度

```
[gnspos] cmd=208 收到 S 条｜解出坐标 P 条（命中 H%）｜当前实体 E 个
         ｜平均采样 P/E｜速率 R 条/秒（F Hz/实体）｜来源=gns-208
```

- `S` 与 `P` 分开记（新字段 `gnsPosSeen`）：`S=0` 是「没有位置消息」，
  `S>0 而 P=0` 是「消息结构变了」—— 两种完全不同的故障，以前分不开；
- `R`/`F` 是新字段 `gnsPosFirst` 算的真实速率。以前只有累计条数，
  「1.7 Hz」和「64 Hz」两种说法都说得通，没法判断画面会不会卡。

### 3. `[dec]` 标来源

```
[dec] ... 玩家=13(来源=gns-208) 最佳=无
```

真坐标和启发式给出的数字在形态上完全一样，不标来源就必然被误读 ——
这一轮就是被它误读了两次。

### 4. `[gnsmsg] 按字节量排前8`

```
[gnsmsg] 按字节量排前8 78×2(均880) 207×141(均120) ...
```

按**条数**排的话完美平台 UI（cmd=207）永远霸榜，实体快照「条数少、每条几百上千字节」
被挤到十名之外 —— 于是「这局到底有没有实体消息」这个问题一直没有答案。
新增 `gnsMsgBytes` + `gnsTopCmdsByBytes()`，按累计字节量排。

## 七、下一局只看三行

```
[gnspos] cmd=208 收到 S 条｜解出坐标 P 条（命中 H%）｜当前实体 E 个｜速率 R 条/秒（F Hz/实体）
[gnsmsg] 按字节量排前8 ...
[dec] ... 玩家=N(来源=gns-208) ...
```

判据：

1. **`来源` 必须是 `gns-208`**。出现别的值说明 gnsPos 空了，退回了启发式。
2. **`E` 是画出来的目标数**。10 上下正常；60 多说明把投掷物/掉落的枪也算进去了
   （需要按实体索引区间过滤，等下一轮定）。
3. **`H` 应接近 100%**。掉下来说明 blob 结构变了。
4. **`F` 决定画面流畅度**。低于 5 会一跳一跳。
5. **`S=0`** ⇒ 这局不在对局内，或者 cmd 号变了。
