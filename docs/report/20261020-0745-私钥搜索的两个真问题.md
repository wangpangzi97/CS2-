## 二、证据一：私有大堆只拿到自己 1.1% 的字节

```
[key] 快照计划：邻域 53.6 MB｜小区域≤256KB 551.8 MB｜中区域≤1MB 412.9 MB
       ｜私有大堆 6253.4 MB｜映射区 305.8 MB｜映像/其它 84.9 MB｜预算 1024 MB
[key] 快照实抓：小区域≤256KB 551.3 MB｜中区域≤1MB 400.9 MB｜私有大堆 **71.8 MB**
[key] 冻结情况：冻结 267ms｜已恢复｜抓取 1048576 KB｜**达到上限被截断**
```

`snapRanges` 原来是**按档位严格排序、先到先得**：

```
tier0 小区域 → tier1 中区域 → tier2 私有大堆 → tier3 映射区 → tier4 映像
```

小区域 551.8 + 中区域 412.9 = **964.7 MB**，把 1024 MB 的预算吃到只剩 59 MB。
于是**私有大堆只拿到 71.8 MB —— 占它自己 6253 MB 的 1.1%**。

而新分配的 32 字节密钥对象，正是住在私有大堆里的。**根本没被读到。**

### 修法：配额制

```go
var snapTierQuota = [...]float64{0.30, 0.15, 0.45, 0.07, 0.03}
```

每档保底拿一份，用不完的让给后面的档。1024 MB 预算下的新分配：

| 档位 | 原来 | 现在 |
|---|---|---|
| 小区域≤256KB | 551.3 MB（全拿） | 307 MB 配额（实际 551 MB 全装得下 → 仍全拿） |
| 中区域≤1MB | 400.9 MB | 153 MB 配额 |
| **私有大堆** | **71.8 MB** | **460 MB**（6.4 倍） |
| 映射区 | 0 | 71 MB |
| 映像/其它 | 0 | 30 MB |

小区域仍然排第一（公钥确实在 20~192 KB 的区域里，硬规则依据见 `snapSmallMax`），
但不再能独吞整个预算。

`[key]` 现在会多打一行，让「计划 vs 实抓」的差能一眼对上：

```
[key] 快照配额（每档保底，用不完让给后面的档）： 小区域≤256KB=307MB 中区域≤1MB=153MB
       私有大堆=460MB 映射区=71MB 映像/其它=30MB
```

## 三、证据二：CCrypto 扫不到，更像 nonce 错，不像密钥不在

```
[gnsmem] conn @0x182d2990b70  connID 2a7d1219/77e5526d
         IV1=b5f2cdd8731c71ef3965fd49 IV2=3b82bd9f01992691ed513b41
         crypt 0x1834c0fcd80/0x1834c0fce40
[gnsmem] 0x1834c0fcd80 起 4096 字节内试了 302 个候选窗口，都不对
[gnsmem] 0x1834c0fce40 起 4096 字节内试了 291 个候选窗口，都不对
```

**这条推理很关键**：CCrypto 里装的是**派生出来的 AES 会话密钥**，游戏自己
每一帧都要用它加密 —— 它**必然在内存里**，不可能被擦掉（被擦掉的是 X25519
私钥，那个只在握手期活着）。

所以「4096 字节 × 302 个候选窗口全部 GCM 验证失败」几乎只有一种解释：
**nonce/IV 派生不对**。正确的密钥大概率就在这 302 个里，只是配错了 nonce，
128 位认证标签自然一个都过不了。

已把这段推理写进日志（`gnsmem.go`），免得下一轮继续往「扩大扫描范围」上使劲：

```
[gnsmem] ⚠ 注意：派生出的 AES 密钥**必然在 CCrypto 里**（游戏每帧都要用它加密），
         所以上面全不过更像是 **nonce/IV 派生不对**，而不是密钥不存在。
[gnsmem]   下一步优先查 GNSIVForSeq 与帧头包序号解析，别急着调大 -snap-mb。
```

## 四、KDF 材料这次是齐的，只差私钥或正确 nonce

`gns-kdf-20261020-072945.json` 里除了两把 IV，还有：

```
client_conn_id = 2a7d1219      server_conn_id = 77e5526d
send_iv = b5f2cdd8731c71ef3965fd49
recv_iv = 3b82bd9f01992691ed513b41
salt_a_mem = a0ae726ee7b600be   ← 等于 server_nonce_wire
salt_b_mem = 5579530964c4b1ce   ← 等于 client_nonce_wire
wire_client_cert  (97 B)  wire_server_cert  (97 B)
wire_client_crypt (49 B)  wire_server_crypt (49 B)
```

`wire_client_crypt = 08 01 12 20 <client_eph_pub 32B> 19 <client_nonce 8B>`，
和日志里的 `客户端临时公钥 7803eefb…` 完全对上。

**新拿到的一条**：内存里的 16 字节盐是 `[server_nonce, client_nonce]` 顺序，
与线上握手报文的顺序相反。这是之前几轮一直没定下来的 KDF 输入顺序。

同时 `raw_scan` 显示四个握手 blob 在内存里**一个都搜不到**
（`client_cert@未找到｜server_cert@未找到｜client_crypt@未找到｜server_crypt@未找到`）——
说明 GNS 在派生完密钥之后就把这些握手缓冲释放/擦掉了。这和「私钥捞不到」是同一件事。
