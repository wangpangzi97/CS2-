## 0 结论

问："是否可以还原代码，或者做一个一样的、实现雷达？"

**分三档回答，别混为一谈：**

| 档位 | 能否 | 说明 |
|---|---|---|
| **A. 还原成原始 `.go` 源码** | ❌ **做不到** | Go 编译产物里没有 AST、没有类型信息、没有注释、没有变量名。能拿回来的只有"函数名 + 机器码" |
| **B. 等价重构（同架构、同算法、可编译、可运行）** | ✅ **已完成并实测通过** | 3,244 行 Go，`go build` 与 `go vet` 全绿，跨进程实测把 X25519 私钥挖出来（逐字节一致） |
| **C. 做成能直接出雷达画面的成品** | ⚠️ **差最后一层** | 缺的是 CS2 那侧"用密钥解密包 → 解出玩家坐标"的协议解析。这层**原程序里也没有**——它把密钥和原始包交给服务端/内置 parser |

一句话：**"还原源码"是做不到的，"做一个一样的"已经做出来了，而且核心那一步（进程密钥）是实测跑通的。**

## 1 为什么"还原源码"做不到

这不是工具不够好的问题，是 Go 编译模型决定的：

| 原始源码里有 | 编译后还在吗 |
|---|---|
| 函数名（含包路径） | ✅ 在 `.gopclntab` 里，已全部取出（启动器 7,384 个 / 采集器 3,816 个） |
| 变量名、参数名 | ❌ 全部丢失，只剩栈偏移 |
| 结构体字段名 | ❌ 只剩 `+0x10` `+0x30` 这种偏移 |
| 类型信息（部分） | ⚠️ 仅够支撑反射/接口，不足以重建源码 |
| 注释、格式、控制流写法 | ❌ 全丢 |
| 内联后的函数边界 | ❌ 已被抹平 |

所以业界把这件事叫 **反编译（decompilation）/ 逆向重构**，不叫还原。产出物永远是"读起来像源码的等价实现"，不是原源码。

**能做的最好的事**，就是我们这次做的：把每个函数的语义逐条挖出来，用干净的 Go 重写一遍，再用实测证明重写的行为和原程序一致。

## 2 重构产出的架构

```
rebuild/cs2radar/
├── go.mod                     module local/cs2-radar   ← 与原程序模块名一致
├── internal/
│   ├── winapi/                Win32 绑定（OpenProcess / ReadProcessMemory / NtSuspendProcess / DPAPI …）
│   ├── memscan/               进程查找、句柄打开、区域枚举、读取、冻结/恢复

│   ├── keyfind/               ★ 密钥搜索：hint / anchor / window / pointer + verifyPriv
│   ├── pcapdev/               抓包：wpcap.dll 优先，原始套接字回退
│   ├── transport/             管道帧协议 + NDJSON 事件 + IPv4/UDP 解析
│   └── license/               设备身份（DPAPI + Ed25519）+ 卡密签名（challenge-response）
├── cmd/
│   ├── collector/             等价于 capture.exe（同名 flag 全集）
│   └── launcher/              等价于 CS2radar-v2.0.5.exe（本地页面 + SSE 替代 Win32 窗口）
└── tools/
    ├── plantkey/              验证靶标：把已知私钥埋进自己内存
    └── keyscan/               用重构的搜索器去挖，自动判定 PASS/FAIL
```

**无任何第三方依赖** —— 全部标准库（`syscall` + `NewLazyDLL`），与原程序做法一致，`GOPROXY=off` 也能编译。

### 4.3 跨进程端到端（最强的一条）

`plantkey.exe` 把一把随机 X25519 私钥埋进自己 4 MB 堆 → `capture.exe` / `keyscan.exe` 用**另一个进程**的身份去挖：

```
pid=34924
pub =05052827d6b5a399a8554c22404e0f2f9604b7a8d638740ec08543037d72ba01
priv=58b5f7259f53102bf11133eabd03eb016bb646d55e4193b0ff0944a82bceedb8

---- 采集器只查元数据（0x400，不读内存/不挂起）----
pid=34924 readable_regions=112 readable_bytes=34942976 writable_bytes=21311488

---- 跨进程搜索密钥（0xC10）----
FOUND tag=window addr=0xc000016400 priv=58b5f7259f53102bf11133eabd03eb016bb646d55e4193b0ff0944a82bceedb8
      elapsed=1.0166783s
VERDICT=PASS 搜索到的私钥与预埋值逐字节一致
```

**含义**：`OpenProcess(0xC10)` → `VirtualQueryEx` 枚举 112 个可读区域 → 暴力搜索 → 1.02 秒命中 → 私钥逐字节正确。这就是 CS2 雷达拿"进程密钥"的全过程，在真实 Windows 上跑通了。

## 5 与原程序的差异（必须说清，不能假装 100% 一样）

| 项 | 原程序 | 重构 | 影响 |
|---|---|---|---|
| 密钥搜索触发 | 250 ms ticker 持续轮询 cs2.exe | 收到握手公钥后触发一次 | 行为等价；未复刻轮询节奏 |
| 启动器 ↔ 采集器通道 | `CreateNamedPipeW` + `DuplicateTokenEx` + `SetEntriesInAclW`（提权子进程回写） | 子进程 stdout 管道 | 功能等价，少了跨完整性级别的 ACL 处理 |
| 启动器界面 | Win32 原生窗口（`createWindowAt`/`paintWindow`/`buttonProcedure`） | 本地 HTTP + SSE 页面 | 功能等价，交互不同 |
| 提权 | `IsUserAnAdmin` → `ShellExecuteW("runas", ...)` | 已实现 `IsAdmin()`，但未自动重启 | 需手工以管理员运行 |
| CS2 包解析器 | 内置（密钥 → 解密 → 出坐标） | **未实现** | 见下 |
| 帧内 kind 取值 | 未知（只确证长度前缀与 3 条错误文案） | 自定义 0x01/0x02/0x03 | 不影响自洽，但与真品不互通 |
| 窗口扫描步长 | 未还原（只确证指针链是 8） | 默认 8，可配 | 见 §6 第 1 条 |

### 关于"差最后一层"

原程序**自己也不解密 CS2 的包**。已确证（report §3.7）：`AES-CBC`、`AnswerLength` 这些串属于 Go 标准库（FIPS 自检 / DNS 库），**雷达本身不做 AES-CBC 解密**。

它的分工是：**采集器负责"进进程挖私钥 + 抓原始 UDP 包"，然后把 `密钥 + 包` 交给下游**（内置 parser / 服务端）。所以"最后一层"（用 X25519 共享密钥解出玩家坐标）属于**另一个组件**，不在 v2.0.5 这两个 EXE 里。

要补上这一层，需要的是 CS2 协议知识（`svc_EncryptedData` / `tv_encryptdata_key` 之后的消息结构），不是继续逆向这两个 EXE 能得到的。

## 6 局限（诚实清单）

1. **窗口扫描步长是取舍，不是还原**。逆向只确证了指针链用 8 字节步长。测试给出了证据：非 8 对齐的落点用默认步长会漏过，改成 1 就能命中（实测）。实战中 Go/C++ 分配器给出的对象起始地址都是 8 字节对齐，所以默认够用。
2. **签名消息的 s1/s2/s3/bool/int64×2 语义仍未确定**。只有第一个字段（卡密哈希）是实证的。重构里把服务端 challenge 放 s1、本地随机 nonce 放 s2，属于"形状正确、字段待确认"。
3. **服务端未探测**。`https://154.12.82.177` 的 challenge/login/check 实际响应格式、换绑扣天规则均未获取（VM 内无 `-login.bin`，说明那台机器从未成功登录）。
4. **未在真实 CS2 上验证**。跨进程验证用的是自造靶标（私钥埋在普通堆里）。真实 `cs2.exe` 的密钥可能在被反作弊保护的页、或需要更复杂的锚点策略。
5. **`hsInfo` 的 field1(32 位)/field3(64 位) 语义未定**。
6. **窗口扫描是 O(字节数/8) 次 X25519 标量乘**，纯暴力路径慢。原程序靠 hint（上次命中地址）+ anchor 让常规路径秒级完成；重构保留了这个顺序，并额外加了 `MaxCandidates` 预算（原程序无此字段）。

## 8 下一步

1. **接上最后一层**：在 `cmd/collector` 里加 CS2 包解析（X25519 共享密钥 → 解密 → 提取玩家坐标），输出到本地雷达页面。这一步需要 CS2 协议资料，不是继续逆向这两个 EXE 能得到的。
2. **动态对齐原程序**：用 Frida hook 原程序的 `crypto/ed25519.sign`（启动器 0x11f780）打印明文签名消息，把 s1/s2/s3/bool/int64×2 逐字定死；hook `verifyPriv`（capture.exe 0x179ea0）确认真实 CS2 的命中地址形态与耗时。
3. **补 `-pid` 轮询节奏**：把 250 ms ticker + pid 变化重开句柄的行为按原样复刻。
4. **管道层对齐**：用 `CreateNamedPipeW` + `SetEntriesInAclW` 复刻原程序的跨完整性级别通道，便于把启动器与采集器拆成两个独立进程。
