## 1 端到端工作流程

**默认形态 = 本机方案（与原版 v2.0.5 一致）：所有环节都在同一台 Windows 上完成，
位置数据不出本机，零对外网络连接。**

```
┌─────────────────────── Windows（需管理员）───────────────────────┐
│  capture.exe（采集器，内嵌解码器 + 雷达页）                        │
│                                                                   │
│  ① resolvePID()        定位 cs2.exe                               │
│  ② keyfind.Search      读内存挖 X25519 私钥   ← 详见 §2            │
│  ③ pcapdev             抓该进程方向的原始 UDP 载荷                 │
│  ④ uplink.Sender       每 64 包 / 200 ms 批量投递                  │
│  ⑤ radarsrv.Store      同一进程内解码（见下）                      │
│  ⑥ http 127.0.0.1:8766 /radar 出画面（浏览器访问本机地址）         │
└───────────────────────────────────────────────────────────────────┘
        ④ 的出口是可切换的：默认 local（同进程），可选 remote（公网）
```

`radarsrv.Store`（本机模式下内嵌在采集器里）做的六件事：

```
⑤ ingest              收批次，分方向累积到帧缓冲（上限 MaxFrames）
⑥ SharedSecret        ECDH(clientPriv, serverPub)  ← 数学确定
⑦ ProbeFrom           枚举 ~720 候选方案 + 自动打分   ← 详见 §3
⑧ decode              解密 → netmessage 分帧 → 坐标提取
⑨ Snapshot            出画面（JSON + Canvas 页面）
```

### 可选形态：远端服务器解码

给 `capture.exe` 加 `-uplink https://<服务器>:8899/api/v1/ingest`，
则 ④ 改为走 HTTPS 上行，⑤–⑨ 由 `cmd/radarserver`（systemd）执行。
**解码代码是同一份**（`internal/radarsrv`），只是宿主进程不同。

```
┌────────────────────── Linux 109.206.245.172:8899 ────────────────┐
│  radarserver（systemd: cs2radar.service，cmd/radarserver 薄封装） │
│  ⑤ ingest  ⑥ SharedSecret  ⑦ ProbeFrom  ⑧ decode  ⑨ /api/v1/radar │
└───────────────────────────────────────────────────────────────────┘
```

**为什么把解码做成可切换的包**：原版 v2.0.5 自己不解密（它把密钥和包交给下游），
"共享密钥 → 会话密钥 → 明文"这一层不在这两个 EXE 里。
把它抽成 `internal/radarsrv` 之后：
- **默认**内嵌进采集器 → 本机解码，与原版形态一致，位置数据不出本机；
- **可选**由服务端复用 → 机器性能不够时把解码挪走（候选枚举可慢慢试，方案变更只改服务端）。

## 2 客户端获取密钥的详细流程（`internal/keyfind`）

核心判据只有一个，且是**数学确定**的：

```go
// verifyPriv：把候选 32 字节当 X25519 私钥，算出公钥，与握手公钥逐字节比对
pub := ecdh.X25519().NewPrivateKey(cand).PublicKey().Bytes()
return bytes.Equal(pub, targetPub)
```

没有"猜一个试试看"的成分 —— 错一位就必然不等。所以**不存在假阳性**。

四条搜索路径（`FindPrivWithHints` 依次尝试，命中即返回）：

| 路径 | 标签 | 做法 | 依据 |
|---|---|---|---|
| 1 | `hint/udp4` | 抓包时顺手记下"载荷里出现过握手公钥"的内存地址，优先在附近找 | 逆向确证的调用顺序：先拿到握手包，再挖私钥 |
| 2 | `pointer` | 从命中点读 8 字节指针（落在 `[0x10000, 0x7FFFFFFFFFFF]` 才算），跳到目标地址再读 32 字节 | 逆向确证的指针链是 **8 字节步长** |
| 3 | `adjacent/anchors` | 在命中点相邻区域扫锚点 | 堆上对象常连续排布 |
| 4 | `window` | 滑窗全扫，默认 8 字节对齐；**`WindowStride=1` 可命中非对齐落点** | 实测：非 8 对齐落点用默认步长会漏过，改 1 就命中 —— 这是个**有证据的取舍** |

配套的保护（都实测过）：
- `OpenProcess(0xC10)` = `VM_READ | QUERY_INFORMATION | SUSPEND_RESUME`（读+挂起）；只查元数据时用 `0x400`，不读内存、不挂起；
- `FreezeFast`/`ThawFast` 在扫描期间短暂挂起游戏；**恢复失败会打印"游戏恢复调用未成功，请立即停止工具"**；
- `recoverWorker` 把每个工作协程的 panic 兜住，避免扫描中途整程序挂掉；
- `MaxCandidates` / 扫描 deadline / `budgetExceeded()` 三重预算，防止在无匹配时无限扫。

## 3 服务器侧的方案定位（`internal/cs2crypto`）

- `SharedSecret(clientPriv, serverPub)` —— **确定**，无需搜索。
- 未知的是：**KDF（含 info/salt）、AEAD 类型、nonce 构造、密文起始偏移**。
- 处理办法：**枚举候选 + 自动打分**，判据是"解密结果能否切成合法的 netmessage 流"（`varint cmd + varint size + payload`，必须正好消费完整段）。
- 成立判据：`ok >= 3 && ok*2 >= frames`（挡掉无 AEAD 的流式候选偶然解出 1 帧）。
- 随机字节误判率实测 **0/200**。

实测命中：`hkdf-sha256/info-empty | aes-256-gcm | ctr-le-u64 | off=2`，**60/60 帧**，Top-2 仅 2/60。

### 遗留（真机联调时优先怀疑）
1. **nonce 序号与发送方计数器的对齐**。当前用"绝对帧序号"当 nonce 计数器。前提是：抓包无丢包、且从计数器 0 开始抓。真实流量若丢包或中途开始抓，会全部解不开。
   → 扩展方向：给候选加"nonce 基址"维度，或让采集器把**每包抓取序号**一并上行。
2. **候选空间可能不覆盖真实方案**。若真实 KDF 的 info 串不在表里、或用了 ChaCha20-Poly1305、或带 AAD，搜索会失败。
   → `/api/v1/probe` 会列出全部落选方案，按 OK 帧数分布判断往哪扩。
3. **坐标提取是启发式的**，不是真解码器。接上真实 CS2 实体 schema 后实现 `cs2proto.Decoder` 替换。
4. **未在真实 CS2 + 真实抓包上验证过**（环境限制）。

### 本次修掉的 3 个 bug（都有回归测试锁死）

| bug | 根因 | 修复 | 测试 |
|---|---|---|---|
| **幽灵目标** | `decode()` 每次 ingest 都从头重喂全部帧；重喂时槽位已在最新位置，位移 > 关联半径(256) 的目标会在历史坐标处重新建槽。p2 位移 303 > 256，故多出恰好 1 个 | 改增量：`fedDir`/`fedFrames` 游标 + 锁内原子领取帧区间 | `TestDecodeIsIncremental`（旧逻辑 3→6） |
| **槽位存活记账** | 用"以槽位下标为键的 `lastSeen` 旁路表"记存活时间，而 `Snapshot()` 会压缩 `slots` 数组导致下标错位 | 直接读 `Player.UpdatedAt` | 同上（第二次 Snapshot 返回 0 个槽位） |
| **丢帧后解码停摆** | 帧缓冲有上限，超出时丢最旧的；游标用缓冲区下标 → 触顶后 `start == len(frames)` 永久成立，解码静默停止；且丢帧后 nonce 错位 | 游标改**绝对帧序号**，`ProbeFrom` 增加 `base` 参数 | `TestDecodeSurvivesBufferTrim`（旧逻辑游标卡在 30） |
