## 0 一句话

采集器挖到 X25519 私钥、抓到原始 UDP 包后**原样上行**；服务器用「私钥 + 握手公钥」算出共享密钥，**自动搜索**出会话密钥的推导方式与 AEAD 方案，把密文还原成 netmessage 流，再解出玩家坐标。整条链路已用真实二进制端到端跑通。

---

## 1 这一层到底缺什么

先说清楚，避免误解：

| 环节 | 状态 | 依据 |
|---|---|---|
| 抓包、挖私钥 | ✅ 已还原 | `report/report.md` §3（`OpenProcess(0xC10)` + X25519 暴力搜索） |
| X25519 共享密钥 = ECDH(客户端私钥, 服务端公钥) | ✅ **数学上确定** | X25519 定义，无需猜测 |
| 共享密钥 → 会话密钥的 KDF（info/salt 串） | ❓ **未知** | 不在 v2.0.5 的两个 EXE 内 |
| AEAD 类型、nonce 构造、AAD、密文偏移 | ❓ **未知** | 同上 |
| netmessage 分帧（varint cmd + varint size + payload） | ✅ 确定结构 | Source 2 通用，社区解析器一致 |
| 玩家坐标在实体数据里的具体字段 | ⚠️ 启发式兜底 | 需要 CS2 实体 schema |

**为什么 KDF/AEAD 未知**：原程序自己也不解密。已确证（主报告 §3.7）它把 `密钥 + 原始包` 交给下游（内置 parser 或服务端），`AES-CBC` 那些串是 Go 标准库噪音。所以这一层在客户端侧根本不存在，只能靠**握手材料本身**推。

## 2 处理"未知"的办法：把猜测变成可搜索空间

不猜一个然后祈祷，而是**枚举 + 自动打分**。

**打分判据**（`cs2proto.Score`）：把候选方案解密出来的明文丢给 netmessage 分帧器，要求
- 正好消费完整段（不多不少）
- 每条消息 `cmd ≤ 256`、`size` 与剩余长度自洽
- 至少一条非空消息

方案选对 → 绝大多数帧都能完整解析；选错 → 是随机字节，几乎全部失败。实测随机字节的误判率是 **0/200**，所以这个判据非常干净。

**候选空间**（`cs2crypto`）：

| 维度 | 取值 | 数量 |
|---|---|---|
| KDF | `raw`、`sha256`、`hkdf-sha256/{info-empty, info-cs2, info-cs2-radar-v1, info-netkey, info-connection-key}` | 7 |
| salt | `nil` / 服务端公钥（仅对 hkdf 生效，避免等价重复项） | ×1~2 |
| AEAD | `aes-256-gcm`、`aes-128-gcm`、`xor-sha256-ctr`（排除"其实没上 AEAD"） | 3 |
| nonce | `ctr-le-u64`、`ctr-be-u64`、`ctr-le-u32`、`prefix4-ctr-le-u64` | 4 |
| 密文偏移 | 0..`max-offset`（默认 4） | 5 |

合计约 720 个组合，每组合解密 N 帧 —— 200 帧量级下 15 万次 AEAD 运算，毫秒到秒级。

**成立判据**：至少 3 帧、且过半帧可解（`ok >= 3 && ok*2 >= frames`）。这一条挡住"无 AEAD 的流式候选偶然解出 1 帧"的假成立。

## 3 整条流水线

```
采集器 (capture.exe)                        服务器 (radarserver.exe)
─────────────────────                       ─────────────────────────
① 抓 UDP 原始包  ─┐
② 挖 X25519 私钥 ─┴─→ POST /api/v1/ingest ─→ ③ X25519 共享密钥（确定）
                                             ④ 方案自动搜索（枚举+打分）
                                             ⑤ netmessage 分帧
                                             ⑥ 坐标提取 → 雷达画面
```

对应代码：

| 环节 | 位置 |
|---|---|
| ① 抓包 | `internal/pcapdev`（Npcap 优先，raw socket 回退） |

### 6.5 修掉的一个真实缺陷：「幽灵目标」

**现象**：远端 60 帧、3 个玩家的回放，画面稳定出现 **4 个目标**（本地却是 3 个）。

**根因（可精确推导，非猜测）**：

1. 客户端 `Close()` 在发完数据后还会发一个**空批次**；而服务端**每次 ingest 都 spawn 一次 `runProbe + decode`**，所以 `decode()` 被调用多次是常态。
2. 原 `decode()` 是"**从头重喂全部帧**"。重喂 tick0 时，槽位已经在 tick59 的位置。
3. 关联半径是 256 单位。合成数据里三个玩家 60 帧的位移分别是：p0 ≈ 172、p1 ≈ 231、**p2 ≈ 303**。
4. 只有 p2 越过了 256 → 它 tick0 的历史坐标被当成**新目标**重新建槽。所以多出来的目标**恰好是 1 个**，且全部是 `cmd=7`（p2）在 tick0 的坐标 —— 与诊断日志逐行吻合：

```
#0 cmd=6 pos=(-568.82, 947.64, 72.00)   ← p1@tick0
#1 cmd=7 pos=(-514.31, -89.01, 80.00)   ← p2@tick0
#2 cmd=5 pos=(1199.99,  2.88, 64.00)    ← p0@tick1（tick0 是整数坐标，被判据过滤）
#3 cmd=7 pos=(-514.31, -89.01, 80.00)   ← 重复建槽（p2@tick0）
#4 cmd=7 pos=(-514.31, -89.01, 80.00)
#5 cmd=7 pos=(-514.31, -89.01, 80.00)
```

**修复**：`decode()` 改为**增量**，用 `fedDir` / `fedFrames` 游标记录"已喂过的方向与帧数"，并在**锁内原子领取**帧区间（防止并发 ingest 的多个 decode 协程重复喂同一批）。方向切换时 `decoder.Reset()` 后从头喂。

**验证**：
- 新增回归测试 `cmd/radarserver/main_test.go::TestDecodeIsIncremental`。**还原旧逻辑后该测试失败：`首次 3 个，重复 3 次后 6 个`**；修复后通过。
- 本地压力复现：同一会话**连续重放 3 次**，目标数恒为 **3**，日志显示后续 decode 全部 `新解帧=0`。

> 另修：`HeuristicDecoder` 原来用"以槽位下标为键的 `lastSeen` 旁路表"记存活时间，而 `Snapshot()` 会压缩 `slots` 数组导致下标错位 → 槽位被误判过期。已改为直接读 `Player.UpdatedAt`（见 `internal/cs2proto/entity.go` 注释）。

## 7 局限（诚实清单）

1. **候选空间可能不覆盖真实方案**。若真实 KDF 的 info 串不在表里、或用了 ChaCha20-Poly1305（Go 标准库没有，本版未实现）、或带 AAD，搜索就会失败。扩展方式很直接：往 `KDFs()` / `Ciphers()` / `NonceSchemes()` 加条目即可，打分逻辑不用动。**如果 Top-1 不成立，`/api/v1/probe` 会把全部落选方案列出来，便于判断该往哪个方向扩。**
2. **坐标提取是启发式的，不是真解码器**。`ScanFloat3` 先按 protobuf 字段边界取长度恰好 12 的字段当 3 个 float32（这条不会误读边界，零假阳性），取不到才退回滑窗兜底。真实 CS2 的实体数据可能是三个独立 float 字段、或量化整数、或需要 entity delta 还原 —— 这些都需要 CS2 实体 schema。**接缝已留好**：实现 `cs2proto.Decoder` 接口替换掉 `HeuristicDecoder`，服务器其余部分不用改。
3. **没有在真实 CS2 流量上验证过**。合成靶标用的是真实 X25519 + 真实 AES-GCM，但"服务端"是本地造的。真实流量的密文偏移、是否有包头、是否分片，都可能不一样 —— `-max-offset` 就是为这个准备的旋钮。
4. **单向流**。当前只在**一个方向**（优先 `s2c`）上搜索方案并解码。真实链路两个方向的密钥/nonce 可能独立，需要分别搜索（代码结构已支持，只是没同时跑）。
5. **回放模式没有"重放时序"**。`-replay` 会把整批包一口气上行，不模拟真实时间间隔。用于验证链路足够，用于压测不够。
6. **nonce 序号直接用了缓冲区下标**（`OpenFrame(i, frame)`）。这在"抓包无丢包、且从计数器 0 开始抓"时成立（合成靶标就是 60/60 命中）。真实流量有两个风险：
   - **丢包**：UDP 丢一包，下标与发送方计数器就错位，之后全部 GCM 校验失败；
   - **中途开始抓**：第一个抓到的包，其计数器未必是 0。
   → 真机联调时若 `/api/v1/probe` 全部落选，优先怀疑这两点。扩展方向：给候选加一个"nonce 基址"维度，或让采集器把**每包抓取序号**一并上行、由服务器按序号推计数器。
