## 1 卡死

### 1.0 真根因：窗口线程没锁（`runtime.LockOSThread` 漏了）

> 这一条是**后补的**，也是用户"卡死"的主因。下面 1.1/1.2 的日志无界增长
> 确实存在，但按 ~180 字符/5 秒的速率要跑十几分钟才显形 —— 解释不了
> "启动 7 秒就卡死"。真正的原因在下面。

**Windows 的消息队列是 per-OS-thread 的**：窗口建在哪个线程，它的消息
（`WM_TIMER` / `WM_CLOSE` / `WM_PAINT`…）就只进那个线程的队列。

而 **Go 的 goroutine 会在 OS 线程之间迁移**。`GetMessageW` 是阻塞调用，
执行期间 M 被独占、不会迁移；但**两次 `GetMessageW` 之间**的 Go 代码
（`refreshStatus`、`DispatchMessage` 等）可以被调度到另一个 OS 线程上。
一旦发生，消息循环就跑到新线程的（空）队列上等消息，而原线程队列里的
`WM_TIMER` 永远没人取 —— 表现就是：

- 状态栏、日志框**不再刷新**（假死）
- 点"停止"/关闭窗口**没反应**（`WM_CLOSE` 投到了没人处理的队列）

**取证**（`logs/uitest_020627/`）：加毫秒级打点后，一次 30 秒跑的时间线是

```
02:11:30.974  Stop() 被调用
02:11:30.978  抓包侧全部收尾完成（4ms，完全正常）
02:11:30.978  武装 8 秒兜底
              ← 这里什么都没有：WM_CLOSE 根本没被处理
02:11:38.979  8 秒兜底到期，os.Exit(0)
```

抓包侧 4ms 就干净退出了，UI 侧 8 秒内一次都没处理 `WM_CLOSE`。
栈快照里 UI 线程（goroutine 1）停在 `GetMessageW`，**是空闲而不是忙** ——
正是"消息投到了别的队列"的特征。

**修复**：`runGUI` 里创建窗口前 `runtime.LockOSThread()`。

```go
app := &guiApp{}
gui = app
runtime.LockOSThread()   // Win32 GUI 硬性要求，见上
if err := app.create(); err != nil { … }
```

修好后栈里会明确标出 `goroutine 1 [syscall, locked to thread]`，
这是锁定生效的直接证据（修复前只有 `[syscall]`）。

**验证**（同一套打点）：

| 场景 | 修复前 | 修复后 |
| --- | --- | --- |
| `-duration 40s` 正常退出 | 48.2s（40 + 8 兜底） | **40.216s**（+0.216s 收尾） |
| `-duration 120s` 长跑 | — | **120.218s**，0 条异常告警 |
| `WM_CLOSE` 处理 | 从未处理 | Stop→退出全程 **10ms** |
| `UI卡死_*.txt` | 每次必生成 | 不生成 |

### 1.1 次要因素：`capture_stats` 把 Go map 原文灌进 UI

`emitter.emit` 在非 ipc 模式下是 `fmt.Fprintf(os.Stderr, "[event] %s %v\n", …)`。
而 `capture_stats` 的 `filter.ports` 是**几十个端口的数组**、`top_ports` 是 6 条
`端口(计数)` —— 单条 **2000+ 字符，每 5 秒一条**。窗口版把 stderr 接进日志框，
这些机器格式的长行就全进了 EDIT 控件。

### 1.2 日志框只追加、从不裁剪

`flushLog` 用 `EM_REPLACESEL` 往末尾追加，没有任何上限。Win32 EDIT 控件的文本是
连续缓冲，**每次插入都按当前总长重排** —— 文本越长越慢，跑十几分钟就肉眼可见地卡，
最后整个窗口无响应。

截图里还有第三个症状：滚动条停在 1/4 处，说明 `EM_SCROLLCARET` 没把视图带到末尾
（它依赖插入符位置，控件没有焦点时不可靠）。

### 修复

| 位置 | 改动 |
| --- | --- |
| `main.go` `emitter.emit` | `capture_stats` 特判，只输出一行人类可读摘要（`statsSummary`）。**2500+ 字符 → ~180 字符**。原始数据仍照常进 ipc 通道 |
| `gui.go` | 日志框封顶 `maxLogChars = 100000`，超过就从头部裁一批（裁到 3/4）并整体重建控件文本 |
| `gui.go` | 待刷缓冲封顶 `maxPendingLines = 2000`，防 stderr 被瞬间灌爆时 Go 侧内存先炸 |
| `gui.go` | 滚动改用 `WM_VSCROLL + SB_BOTTOM`，不再依赖 `EM_SCROLLCARET` |

裁剪逻辑抽成纯函数 `trimLogLines`，由 `TestTrimLogLines`（5 个子用例）覆盖。

> **测试当场抓到一个真 bug**：累加时把**被裁掉那一行**也算进了返回的字符数
> （返回 60、实际保留 48）。计数漂移会让 `logChars` 虚高 → 越裁越早 → 最后可能
> 每轮刷新都全量重建控件，**反而更卡**。修复：`break` 时把刚加的那一行减掉。
> 这类 bug 只在攒够 100KB 日志后才显形，十几秒的冒烟测试根本发现不了。

## 2 "没效果"：用截图数据反推

### 2.1 先对齐口径（读代码确认）

- `run()` 里 `pkts++` 在**端口过滤之前** → `packets` 是过滤前全量
- `portCnt[srcPort]++` 与 `portCnt[dstPort]++` 各记一次 → `top_ports` 计数是 **src+dst 双份**

### 2.2 重算

```
packets 128254, dropped 122522        → 保留 5732
61284(122390) + 40602(122336) ≈ 122363 个包  ← 同一条流的两端，占全量 95%
17006(5744)  + 64437(5730)    ≈  5737 个包  ← 第二条流
```

`64437` **在白名单里**，`17006` 不在。

### 2.3 结论

**端口过滤工作正常**：它丢掉了一条 122363 包（2800 pps）的无关流
（`61284↔40602`，别的进程），保留了 `64437↔17006` 这条 5737 包
（**133 pps，量级正好是 CS2 游戏流量**）。

真正的问题是：**保留下来的 5737 个包里一个握手包都没有**，`ParseHandshake`
43 秒零命中，所以一直停在"等待握手包"。

### 2.4 代码侧的放大器（都堵掉了）

1. **握手解析被放在端口过滤之后** —— 一旦白名单没覆盖到握手用的端口
   （换进程 / 换端口 / 走了加速器隧道），就**静默地**永远收不到握手。
   失败模式最恶劣的一种。
   → 移到**过滤之前**，且只对 c2s（客户端发出）方向做。c2s 方向确定、包量小。

2. **`startKeySearch` 的 goroutine 只 `select` 一次** —— 首次搜索失败
   （误命中 / 进程刚重启 / 内存没就绪）后永远不再试，卡死在"失败"。
   → 改成**循环**，失败后继续等下一个握手包；`tried` map 防止同一个公钥
   反复触发 10 分钟搜索。

## 3 顺带修掉的

**① 窗口版从来没有自动打开过浏览器。**

`gui.go` 里 `*flagOpenBrowser = !*flagAutoExit` 设了，但读它的是 `runCapture`
（命令行版路径），GUI 版走的是 `runGUI`。与"双击即用"的设计意图不符。
已在 `startCaptureAsync` 成功后调 `openRadar()`。

**② `Stop()` 唤不醒阻塞在 `Next()` 上的抓包主循环。**

主循环的退出判断在**循环顶部**：

```go
for {
    if s.stopped() { …退出… }        // 只在顶部检查
    raw, err := s.h.Next()           // ← 大部分时间卡在这里等包
```

`Stop()` 原本只 `close(stopCh)`，没有任何东西叫醒 `Next()`。本机流量大
（2800 pps）时看不出来，**网卡一安静就要等下一个包才回到顶部**，用户看到的
就是"点了关闭窗口不动"。已给 `pcapdev.Handle` 加 `Interrupt()`，
`Stop()` 里顺手推一个空包把它叫醒（`Next()` 返回 `nil`，上层 `continue`
后立刻检测到 `stopCh` 已关）。

**③ 退出路径没有任何可观测性。**

从 `Stop()` 到进程真正退出中间有 6 步（抓包循环退出 → 关句柄 → 关 uplink →
写诊断报告 → 通知 UI → 消息循环退出），任何一步卡住都表现为"关不掉"。
新增 `traceStop()` 带毫秒打点，一次跑就能看出卡在哪一步 —— 上面 1.0 的
根因就是靠它定出来的。

## 4 新增：让"没效果"和"卡死"都变成可交付的数据

窗口版是双击运行的，用户没机会传命令行参数，所以**诊断报告和运行日志默认都开**，
写到 exe 同目录：

- `诊断报告_年月日_时分秒.txt` —— 抓包侧：过滤前的端口分布（c2s/s2c 分开、
  标注是否在白名单）、`ParseHandshake` 命中数、**c2s 载荷首字节 = 0x22 的包数**、
  自动结论（下面三选一）
- `运行日志_年月日_时分秒.log` —— 日志框的全部内容，含退出路径的 `[stop]` 时间线

| 报告结论 | 含义 | 下一步 |
| --- | --- | --- |
| 命中 > 0 | 握手没问题 | 查解码侧（密钥搜索 / 帧解析） |
| 0x22 的包 > 0 但命中 = 0 | **握手格式与 v2.0.5 逆向不符** | 用报告里的「候选样本」十六进制重推 protobuf 路径 |
| 两者都是 0 | 握手包没进抓包范围 | 时机（先开雷达再进局）/ 加速器 / `proc` 配错 |

另外：抓包满 60 秒仍停在"等待握手包"时，日志框会**主动列出最常见的三种成因**。

若 UI 线程真的被卡住，看门狗会**连拍 3 张**全 goroutine 栈到 `UI卡死_*_N.txt`
（连拍是为了区分"一直卡着"和"偶发停顿"：三张栈一样才是真卡）。

命令行版另有 `-diagnose <file>` / `-dump <file>`（过滤前原始包落 JSONL）/
`-logfile <file>`。

## 6 第二轮：用户现场 —— 握手抓到了，但私钥搜不到

用户用新包跑 1m18s 后的报告：

```
【握手检测】
  ParseHandshake 命中 : 1
  c2s 包载荷首字节=0x22: 1
  候选样本:
  c2s 192.168.0.103:54759 → 120.232.87.34:17003  len=331  22 0d 40 3e 0c 45 11 fe …
```

**这是进展**：上一轮"一直等待握手包"已经解决 —— 握手包抓到了
（源端口 `54759` 确实在白名单里），`ParseHandshake` 也解析成功。
窗口状态从「等待握手包」变成「**失败**」，说明卡在密钥搜索这一步。

`searchKey` 只有一种失败表现：`keyfind` 返回 `ErrNoCandidate`
（区域都扫完了、没找到）。但成因有三种，修法完全不同：

| 成因 | 特征 | 能否修 |
| --- | --- | --- |
| 公钥方向反了（是**服务器发来的**） | 公钥在目标进程内存里一次都不出现 | 要重推协议 |
| 扫描侧没覆盖到 | 公钥在内存里出现，但区域/候选不够 | 可调 |
| 内存读被拒 | `shortReads` 占比高 | 可查 |

### 诊断增强（本轮改动）

原报告只覆盖抓包侧，**密钥侧是盲区** —— 上面三种成因一个都区分不了。已补：

1. **【密钥搜索】章节**：pid / 可读区域数+总大小 / 失败原因 /
   完整搜索统计（`candidates`、`reads`、`bytes`、`shortReads`）。
2. **公钥方向探测** `probePubInMemory`：直接在目标进程里搜这 32 字节，
   报告命中数与地址。**这是判定"方向有没有反"的决定性证据**：
   有命中 → 公钥是客户端自己的（私钥必然也在同一进程，搜不到是扫描侧问题）；
   零命中 → 公钥很可能是服务器发来的，"在客户端内存里找私钥"这个方向本身就不成立。
3. **候选样本 48 → 160 字节**：这个握手包是 4 层嵌套 protobuf，331 字节的包
   只给 48 字节根本看不出字段路径对不对。
4. **报告里打印提取到的 32 字节公钥**：没有它就无法核对
   "内存里搜的"与"包里提取的"是不是同一个东西。

探测放在搜索**失败之后**执行（要扫几百 MB），成功路径不付这个代价；
自身带 256 MB / 20 秒双上限。

## 7 第三轮：搜不到的真正原因 —— 扫描覆盖率只有 0.6%

用户第二次回传（1m40s 现场）：

```
【密钥搜索】
  阶段      : 私钥搜索失败（耗时 25.177s）
  目标进程  : cs2.exe (pid=14368)
  可读区域  : 6292 个，共 7096.4 MB
  公钥在内存: 扫了 256.3 MB，命中 0 处
  搜索统计  : candidates=4000000 checks=4008662 bytes=41661536 reads=16601 shortReads=1840
```

**三个数字说明了一切**：

- `candidates=4000000` **正好等于预算上限**（`-scan-budget` 默认值）
- `bytes=41661536` = **41.6 MB**，而可读内存有 **7096 MB** → 只扫了 **0.6%**
- `公钥在内存: 扫了 256.3 MB` → 上一版的探测也只覆盖 3.6%

**所以上一版报告里"公钥一次都没出现 → 方向反了"的结论不成立** —— 那只是没扫到。
这一点必须先纠正，否则会往错误的方向去改协议。

根因是**扫描策略**：原实现把内存里每个 8 字节对齐位置都当候选私钥、推公钥比对。
候选量随内存大小线性爆炸（7096 MB / 8 ≈ 9 亿），400 万预算只够覆盖 0.6%，
而且从低地址顺序扫 —— 真正的大堆根本没轮到。

### 换思路：先定位公钥，再在附近找私钥

私钥是 32 字节随机数，只能"猜一个 → 推公钥 → 比对"；但**公钥是已知的 32 字节**，
直接 memmem 就能定位。找到公钥后，私钥几乎总在同一结构体或相邻对象里
（实测本机植入的一对密钥相距 **32 字节**）。

| 方式 | 覆盖 | 耗时 |
| --- | --- | --- |
| 盲扫私钥（旧） | 0.6%（400 万候选） | 25 s |
| 定位公钥（新） | **100%** | **约 1.6 s / 7 GB** |

实测吞吐 **4477 MB/s**（进程内拷贝，`ReadProcessMemory` 本身很快）。

### 改动

| 位置 | 改动 |
| --- | --- |
| `memscan.Region` | 加 `Type`（`MEM_PRIVATE`/`MEM_IMAGE`/`MEM_MAPPED`） |
| `sortRegionsForScan` | PRIVATE 优先、同类大的优先、IMAGE 最后 —— 预算花在对的地方 |
| `scanPub` | 全内存 memmem 定位公钥（4 MB 块） |
| `findPrivNear` | 命中点 ±64 KB 内试私钥；没找到再放宽到 ±512 KB |
| `searchKey` | **去掉全量盲扫** —— 0.6% 覆盖率却要 25 秒，期望收益太低 |
| `handshake.ByteFieldCandidates` | 递归挖出包里**所有** 32 字节字段 |
| `targetPubCh` | 容量 1 → 16（装得下多个候选） |

**为什么要穷举候选**：主字段路径是从 v2.0.5 逆向来的，版本一变、或当初认错一层，
取到的就不是客户端公钥，内存里怎么搜都搜不到。现在把包里所有 32 字节字段逐个
当候选试，每个只要一次 memmem —— 比让用户再抓一次包快得多。

### 验证

新增 `TestScanPubThenFindPrivNear`：用**本进程**当目标，往堆上放一对真实生成的
X25519 密钥（放在同一个结构体里，模拟真实布局），完整跑 `scanPub`（真实
`ReadProcessMemory`）→ `findPrivNear`（真实 X25519 比对）：

```
区域 232 个｜扫了 55.0 MB｜耗时 12ms｜吞吐 4477 MB/s｜公钥命中 3 处
命中私钥 @0x10ce4e0，最近的公钥命中点距它 32 字节
```

另有 `TestByteFieldCandidates`（嵌套 / 去重 / 畸形输入不 panic）与
`TestSortRegionsForScan`（排序顺序 + 不改入参）。

## 8 第四轮：私钥搜不到 —— 一个被实测推翻的假设

用户回传 `诊断报告_20261017_152214.txt` 后，结论是：

```
公钥在内存: 扫了 7348.9 MB，命中 6 处
失败原因  : 公钥在内存中（6 处），但附近 512 KB 内没有匹配的私钥
搜索统计  : checks=128882  candidates=0
```

公钥在内存里命中 6 处 —— **方向确认正确、进程也选对了**，只差最后一步。

### 8.1 上一版埋的雷：用 clamp 形态当过滤条件

上一版为了把校验次数压下去，加了这样一层过滤：

```go
func clampOK(b []byte) bool {
    return len(b) == 32 && b[0]&7 == 0 && b[31]&0xC0 == 0x40
}
```

理由是 X25519 运算前会 clamp 标量，所以"私钥存储时就已经 clamp"。

**这个理由是错的。** 本机实测（`ecdh.X25519().GenerateKey` × 1000 次）：

```
满足 clamp 形态的比例: 34/1000 = 3.400%
存储字节首字节=0xe6 末字节=0x9c，clampOK=false，能否用于运算=true
```

libsodium 的 `crypto_box_keypair`、OpenSSL 的 `X25519_public_from_private`、
Go 的 `crypto/ecdh` 都是**保存原始随机 32 字节，在每次运算时对副本 clamp**。

后果：拿它当硬过滤，真正的私钥有 **31/32 的概率被静默丢弃**，
报告上只会写"没找到"，根本看不出是自己过滤掉的。

**修复：所有扫描级别都不再按 clamp 形态过滤。**
`TestUnclampedPrivStillVerifies` 把这个结论钉死 —— 它生成一个确定不满足
clamp 形态的私钥，断言它照样能通过验证。

代价是校验次数涨 32 倍，所以必须靠"分级放大 + 多核并行 + 硬预算"控制时间。
实测数据（`BenchmarkVerifyPriv` / `BenchmarkScanRanges`）：

| 项目 | 实测值 |
|---|---|
| 单次 X25519 校验（单线程） | 38.8 µs |
| 并行等效 | 5.0 µs（16 线程）/ 6.1 µs（扫描实测） |
| 7.3 GB 全量（9.2 亿候选） | 约 90 分钟 → 必须限时 |

### 8.2 扫描器重写

原来的 `findPrivNear` 是**串行 + 逐 8 字节系统调用**，实测有两个硬伤：

1. **只有 1 个 worker 在干活**：任务是按区间分发的，6 个区间就只有 6 个线程。
   实测 15K 次校验本该 40 ms，实际花了 601 ms（正好等于单线程）。
2. 窗口被区域边界裁剪后大量位置根本没试到（用户现场 512 KB 窗口只跑了
   12.9 万次检查，而理论值约 39 万）。

新实现 `scanRangesStat`：

- **块读** 1 MB / 次，而不是逐 32 字节 `ReadProcessMemory`；
- **任务切到 1 MB 一块**再分发 → 任意大小的区间都能吃满所有核；
- 区间先 `mergeRanges` 合并重叠，`subtractRanges` 扣掉已扫过的部分
  （第 5 级"全可写区"天然包含第 4 级"公钥所在区域"，不扣就白扫一遍）；
- 生产者 goroutine 用 `stop` channel 兜底，worker 提前退出时不会漏 goroutine；
- `memscan.Process` 的计数器改成原子量（并发读内存原本是数据竞争）。

### 8.3 分级策略与预算

`runKeySearch`（抽成独立函数，便于测试直接调）：

| 级别 | 范围 | 命中时的耗时 |
|---|---|---|
| 1 | 公钥命中点 ±64 KB | 0.08 s |
| 2 | ±1 MB | 1 s |
| 3 | ±8 MB | 约 70 s |
| 4 | 公钥所在**整块内存区域** | 视区域大小 |
| 5 | 所有可写区域（PRIVATE 优先） | 预算内 |

全部级别共享一个总预算 `-key-budget`（默认 180 秒），超时就停，
报告里明确写"扫了多少 MB、是否被**超时截断**"。

**为什么第 1 级就够（大概率）**：本机实测把私钥和公钥放进同一个结构体
（真实实现最常见的布局），两者距离正好 **32 字节**。

### 8.4 诊断能力：命中点上下文 dump

上一版报告只有统计数字，没法区分两种完全不同的情况：

- **a)** 私钥在，但不在公钥旁边 → 该放大范围 / 换锚点；

## 9 第五轮：改用原版方案「冻结游戏再搜索」，禁止 hook

用户明确要求：

> 以后方案不能在使用 hook 因为不安全，采用原版方案冻结游戏在搜索。一定要安全为主要条件。

这一节回答两个技术问题（都有字节级/实测证据），并把冻结方案的安全边界写死。

### 9.1 先回答：hook 密钥协商会不会被检测

会，而且风险不止"可能被发现"，还有一条**机制性硬门槛**。

| hook 手法 | 检测手段 | 难度 |
|---|---|---|
| inline hook（改函数头 5 字节） | 校验函数头字节 vs 磁盘映像、CRC、`NtQueryVirtualMemory` 查页属性 | 极易 |
| IAT / EAT hook | 比对 IAT 指针是否落在模块自身区间内 | 极易 |
| 注入 DLL | 枚举已加载模块 vs 白名单、`PEB->Ldr` 双向链表比对 | 极易 |
| `CreateRemoteThread` / `NtCreateThreadEx` | ETW `Microsoft-Windows-Threat-Intelligence`、内核回调 `PsSetCreateThreadNotifyRoutine` | 中 |
| 硬件断点（DR0-3） | `GetThreadContext` 读调试寄存器 | 中 |
| `SetWindowsHookEx` | 钩子链枚举、`WH_*` 全局钩子需要 DLL 注入（同样落到上面那条） | 易 |

对我们这个目标还有一条更硬的门槛：**CS2 的 Trusted Mode**。Valve 官方把它定位为
"阻碍作弊开发的最小屏障"，管的就是"第三方文件与游戏交互"。一旦有模块注入进游戏
进程，信任模式立即失效，**进不了 VAC 安全服务器**。这不是"可能被封"，是功能上
直接不可用。

结论：hook 路线不是"风险高一点"，是**方向错了**。

### 9.2 再回答：原版是怎么拿到密钥的

**原版零 hook —— 这是字节级验证过的，不是推测。**

对原版 `capture.exe` 的导入表 + 全字节搜索，以下 API **全部 0 命中**：

```
SetWindowsHookEx  CreateRemoteThread  VirtualProtectEx
WriteProcessMemory  VirtualAllocEx  NtCreateThreadEx
```

整个 API 面里**没有任何写内存 / 注入 / 建远程线程 / 装钩子**的能力。抓包走的是
Npcap 驱动（我们改成 Windows 原始套接字 + `SIO_RCVALL`），完全不碰 `ws2_32`。

它取密钥的链路是纯只读的三级搜索：

```
OpenProcess(0xC10)                       ← 读 + 查询信息 + 挂起/恢复
  → VirtualQueryEx 枚举可读区域
  → scanHints    缓存地址（上次命中的地址先试）
  → scanAnchors  区域评分 + 锚点，chase 指针链
                 （8 字节步长，指针范围 [0x10000, 0x7FFFFFFFFFFF]）
  → scanWindows  滑窗暴力
  → 每个候选 verifyPriv：X25519 推出公钥，与目标公钥逐字节比对
```

**关键差异不在"读得干净"，在"抢时间"。**

客户端拿到握手包、算出会话密钥之后，多数实现会用 `SecureZeroMemory` 之类的
**安全擦除**把临时私钥抹掉（这是密码学库的标准做法）。不冻结的话，等扫到那片
内存，私钥早被抹成 0 了 —— 这才是"公钥能找到 6 处、私钥一处找不到"的最可能解释。

原版为此调用 `NtSuspendProcess` 把目标进程**所有线程的时间停住**：擦除线程根本
没有机会运行，私钥就一直留在内存里，可以慢慢搜完再解冻。原版二进制里专门留了
一句「游戏恢复调用未成功，请立即停止工具」，说明作者很清楚挂起游戏有多危险。

### 9.3 冻结的真实危险：挂起计数不绑定句柄

这是本轮最重要的一条安全事实：

> **`NtSuspendProcess` 的挂起计数不绑定句柄。** 挂起之后即使我们的进程崩溃、
> 被任务管理器杀掉、被反作弊终止，目标进程**仍然保持挂起** —— 用户只能手动
> 结束 `cs2.exe` 再重新启动游戏。

所以"冻结"这个动作不能是"调一下 `FreezeFast()` 然后指望后面会解冻"。必须有
结构性保证。

### 9.4 `freezeRun`：四层解冻保证

```go
func freezeRun(fz freezer, hold time.Duration, fn func()) freezeOutcome
```

| 层 | 保证什么 | 少了的后果 |
|---|---|---|
| 1. `defer` 解冻 | fn 正常返回、提前 `return` 都会走到 | 中途 return 就永久冻结 |
| 2. panic 兜底 | fn panic 时 `recover` 后照样解冻 | 空指针一次，游戏就卡死 |
| 3. 看门狗强解 | fn 卡在系统调用里时，到点由独立 goroutine 解冻 | fn 挂住 = 游戏挂住 |
| 4. 解冻重试 | `NtResumeProcess` 偶发失败，重试 3 次 | 一次失败就放弃 = 游戏卡死 |

`freezeHoldLimit = 6 * time.Second` 是**硬上限**，写死在常量里：

> 安全第一：超过这个时长，看门狗**强制解冻**，哪怕搜索还没做完。
> 宁可这次搜不到（可以再跑一次），也不能让用户的游戏一直停着 ——
> 游戏卡死比搜不到密钥严重得多。

解冻彻底失败（3 次重试全败）时的三重提示，缺一不可：

1. `os.Stderr` 打一行「⚠ 解冻游戏进程失败，游戏会一直卡住 —— 请手动结束 cs2.exe」
2. `em.emit("freeze_thaw_failed", ...)` 让窗口层能弹提示
3. 诊断报告【冻结游戏】行下面追加两行 ⚠⚠ 说明 + 处理办法

### 9.5 冻结窗口里放什么

冻结窗口只放三步（预期约 2 秒）：

```
枚举可读区域 (约 50 ms)  →  全内存定位公钥 (约 1.7 s)  →  ±64 KB 近邻搜索 (约 0.1 s)
```

第 2 级（±1 MB）之后的兜底**必须解冻后再跑** —— 7.3 GB 全量要 90 分钟量级，
放进冻结窗口就是"把游戏冻 90 分钟"，绝对不行。代码上由
`runKeySearch(..., startStage=1)` 保证第 1 级不重复跑。

三档开关：

| `-freeze` | 冻结范围 | 冻结时长 | 取舍 |
|---|---|---|---|
| `full`（默认） | 枚举 + 定位 + 近邻 | 约 2 秒（上限 6 s） | 命中率最高，游戏卡顿 2 秒 |
| `short` | 只冻近邻搜索 | 约 0.1 秒 | 卡顿无感，但定位公钥的 1.7 s 在冻结外，私钥可能已被擦除 |
| `off` | 不冻 | 0 | 完全不动游戏，最安全，但失去抢时间的窗口 |

### 9.6 真进程验证：`NtSuspendProcess` 真的能停住进程

不能只信"调用返回成功"。用 `ping -n 60 127.0.0.1`（每秒一行输出）当靶子：

```

TestFreezeThawCycleStable

```

`time.Sleep(200ms)` 再非阻塞 drain 管道，然后才断言。**测试本身的坑也是坑。**

20 轮循环验证的是"挂起计数不会累积" —— 如果解冻没真正抵消挂起，第 N 轮就会

### 10.2 关键结论：那 6 处命中全是报文副本

把 dump 里的字节按 protobuf 解开，结构非常清楚：

```
0a 31                          字段1，长度 49（嵌套消息）
   08 01                       字段1 = 1（协议版本）
   12 20 <32 字节>             字段2，长度 32  ← 就是这个公钥
   19 <8 字节>                 字段3，fixed64（随机数/时间戳）
   20 0d                       字段4 = 13
   28 02                       字段5 = 2
12 40 <64 字节>                 字段2，长度 64（高熵，密文/签名）
```

也就是说：**内存里那 6 处公钥，前面全都紧挨着 `08 01 12 20`（或至少 `12 20`）
这个 protobuf 字段头** —— 它们是「抓到的握手报文在内存里的拷贝」
（原始缓冲 + 解析后的消息对象），不是密钥材料。

**报文副本旁边永远不会有私钥。** 在这 6 个点附近放大搜索窗口，
无论放到 ±1 MB 还是 ±8 MB，都是在错误的地方找。

这条判据已经写进代码（`wireLike`），报告里会直接写「命中性质：全部是报文副本」，
不用再靠人肉看 dump。

### 10.3 缺陷一：近邻窗口被裁剪到命中点自己那一小块

这是本轮最严重的逻辑错误。旧实现：

```go
lo = max(addr-window, hit.Region.Base)
hi = min(addr+window+32, hit.Region.Base+hit.Region.Size)
```

窗口被**裁剪到命中点自己所在的那一块区域**。而用户的 6 处命中全部落在
16 KB ~ 216 KB 的小区域里，于是：

| 级别 | 设计窗口 | 实际覆盖 |
|---|---|---|
| 第 1 级 | ±64 KB | 0.4 MB（6 个小块） |
| 第 2 级 | ±1 MB | 0.6 MB（被裁到区域边界） |
| 第 3 级 | ±8 MB | 0.6 MB（同样被裁） |

日志第 14、15 行印证：

```
[key] 邻域搜索：读 0.6 MB｜区域 12 个｜校验 76773 次｜短读 3｜耗时 1.977s
[key] 邻域没找到，改扫公钥所在整块区域：6 块，共 0.6 MB
```

**三级窗口加起来只扫了 0.6 MB**，等于根本没放大，直接跳到全内存兜底。
而全内存兜底是 6,968 MB —— 预算内能覆盖的比例小到没有意义。

修法：窗口应当按**地址空间里的绝对区间**去和**全部可读区域**求交
（`nearRangesIn`）。命中点所在的 16 KB 小块外面紧挨着的大堆区、线程栈、
其他分配区都会被覆盖到。这才是"放大窗口"应有的语义。

### 10.4 缺陷二：扫描步长是 8 字节，7/8 的偏移从来没被看过

旧实现：

```go
for off := 0; off+32 <= n; off += 8 {
```

只检查 8 字节对齐的窗口。X25519 私钥是 32 字节**原始随机数据**，
不保证落在 8 字节对齐位置 —— 也就是说 **7/8 的可能性从来没被检查过**。

更糟的是：**当时的测试是过的**。因为 `TestScanRangesFindsPlantedKey` 埋密钥时，
Go 的 `ecdh.PrivateKey` 结构体里还有一份**对齐**的内部副本被命中了，
埋进去的未对齐副本一次都没被检查。测试给的是虚假的安全感。

修法：改成逐字节滑动（`filterScan`，每个偏移 O(1)）。
新增 `TestScanRangesUnalignedKey` 专门把私钥只放在偏移 12345（`12345 % 8 == 1`）
上，扫描范围严格限定在那块缓冲内 —— 这条测试在旧代码上必然失败。

### 10.5 逐字节之后，全内存兜底仍然不现实 —— 以及预筛的真实代价

逐字节意味着 7,572 MB 有 **75 亿个**候选位置。按实测 6.1 µs/次校验：

```
7.5e9 × 6.1e-6 s ≈ 12.7 小时
```

所以必须预筛。预筛的思路是：X25519 私钥是均匀随机 32 字节，
而进程内存里绝大多数窗口是结构化数据（指针数组、ASCII、零填充），
用"不同字节值个数"和"零字节个数"就能廉价筛掉。

但实测数据（`TestPrivFilterPassRate`，本机 55 MB 真实内存采样）说明
**预筛只能降低一个数量级，不能让全量变轻松**：

| 阈值 | 内存通过率 | 7.5 GB 预计校验次数 | 真实私钥漏检率 |
|---|---|---|---|
| 不同字节≥22 且 零≤1 | 7.34% | 5.83 亿（约 59 分钟） | **0.72%** ← 太危险 |
| 不同字节≥24 且 零≤2 | 6.36% | 5.05 亿（约 51 分钟） | 0.010% ← 采用 |
| 不同字节≥28 且 零≤0 | 0.61% | 4839 万（约 4 分钟） | **14.3%** ← 绝对不能用于搜密钥 |

原因是游戏进程里有大量**本来就是高熵**的数据（压缩资源、纹理、加密缓冲），
它们和真私钥在统计上分不开。想靠统计把通过率压到 0.1% 以下，
就必然把 14% 的真私钥一起筛掉。

所以：
- 默认阈值 `{24, 2}`（漏检 0.010%），只在**超过 24 MB** 的扫描上启用；
- 24 MB 以内**不开预筛**，保持零漏检；
- `-priv-filter off` 可以完全关掉预筛（慢，但零漏检）；
- 报告的每一级扫描都会写明「预筛 X」或「未开预筛」。

**结论：真正解决问题的是窗口求交（10.3），不是预筛。**

## 11 第七轮：冻结窗口里不该放「算」—— 顺带回答「冻结太短还是太早」

用户问：

> 会不会冻结时间太短或者冻结时机太早

两份新产物（16:50）先给出了关键数字：

```
[key] 公钥定位：扫 7619.3 MB，命中 6 处（2.225s）
[key] 冻结情况：冻结 6s｜**超时被强制解冻**｜已恢复｜第 1 级：读 0.4 MB｜区域 12 个｜
                校验 433648 次｜短读 0｜耗时 4.294s｜**超时截断（未扫完）**
```

### 11.1 时机：不能更晚，早是对的

冻结发生在**检测到 C2S 握手包的瞬间**。客户端在**发包之前**就已经生成临时私钥，
所以那一刻私钥必然在内存里。再晚只会更差 —— 服务器回包一到，客户端算出共享
密钥，私钥就可能被 `SecureZeroMemory` 擦掉。

**结论：冻结时机不是问题，而且没有更早的余地。**

### 11.2 时长：太短是真的，但根因是冻结窗口里放了不该冻的活

看那行数字：**只读了 0.44 MB，却花了 4.294 秒**。

拆开算：

| 冻结窗口内的动作 | 耗时 | 需要冻结吗 |
|---|---|---|
| 枚举可读区域 | 57 ms | 不需要 |
| 全内存定位公钥（memmem 7.6 GB） | 2.225 s | **不需要** |
| ±64 KB 近邻：读 0.44 MB | ~10 ms | 需要 |
| ±64 KB 近邻：43 万次 X25519 校验 | ~4.3 s | **完全不需要** |

6 秒预算里，**真正必须"冻着做"的只有几十毫秒的读取**，剩下 99% 都是纯计算。
计算放在冻结窗口里毫无收益，却把预算吃光、把游戏卡了 6 秒、还导致近邻扫描被截断
（433,648 次校验没跑完 0.44 MB 的窗口）。

所以正确做法不是把 6 秒调大（那只是让游戏卡更久），而是：

> **冻结期间只做「读」，解冻之后再「算」。**

### 11.3 改法：冻结抓快照，解冻后校验

```
冻结窗口（约 1 秒）：枚举区域 57ms → 定位公钥（已并行化）→ 把 ±8 MB 窗口抄到本地
解冻之后（不受限）：在本地副本上逐字节跑 X25519 校验
```

两头都赚：

| | 改前 | 改后 |
|---|---|---|
| 冻结时长 | 6 s（顶满被强解） | **约 1 s** |
| 冻结期间读取范围 | 0.44 MB（还被截断） | **约 67 MB**（±8 MB × 6 处，与区域求交） |
| 校验在哪跑 | 冻结窗口内（吃预算） | 解冻后（游戏不受影响） |
| 分级搜索 | ±64KB → ±1MB → ±8MB 三遍 | 快照一次覆盖三级，直接跳到「所在整块区域」 |

另外把 `scanPub` 并行化了：原来 7.6 GB 单线程 2.23 秒，而它正好在冻结窗口里，
等于游戏白冻 2.2 秒。按区域切 8 MB 分发给 `numWorkers()` 个 worker，命中用
mutex 汇总、按地址排序保证报告顺序稳定。

### 11.4 新增 `snapshot.go`

| 函数 | 职责 |
|---|---|
| `takeSnapshot(proc, ranges, maxBytes, deadline)` | 冻结期间把字节复制到本地（memcpy 级别），上限 256 MB，超限标记 `truncated` |
| `(*memSnapshot).verify(kf, deadline, st)` | 解冻后在本地副本上跑 `filterScan` + `X25519`，用满所有核 |

关键点：`proc.ReadAt` 的缓冲会被复用，所以必须 `append([]byte(nil), buf[:n]...)`
深拷贝 —— 这一条写错就是"快照全是同一块内存的内容"，测试会立刻发现。

### 11.5 现场数据的另一个重要发现

诊断报告新增的「命中性质」判据第一次发挥了作用：

```

```

## 12 第八轮：17:02 现场定性 —— 快照扩容、高熵降级、预算重算

第七轮的快照方案在真机上跑通了，冻结时长从 6 秒降到 **978 ms**，覆盖从 0.44 MB
扩到 **62.9 MB（142 倍）**。但用户 17:02 的产物暴露出三个新问题。

### 12.1 现场数字

```
[key] 公钥定位：扫 7667.9 MB，命中 6 处（876ms）
[key] 冻结情况：冻结 978ms｜已恢复｜抓取 64419 KB｜副本校验：读 62.9 MB｜
                区域 378 个｜校验 215500 次｜短读 0｜耗时 1.972s
[key] 邻域搜索：读 0.0 MB｜区域 0 个｜校验 0 次｜短读 0｜耗时 0s
[key] 邻域没找到，改扫公钥所在整块区域：6 块，共 0.8 MB
[key] 区域扫描：读 0.5 MB｜区域 6 个｜校验 507749 次｜短读 1｜耗时 11.537s
[key] 转入全内存可写区兜底：5268 块，共 7068.9 MB（已扣掉扫过的 0.8 MB）
```

### 12.2 结论一：覆盖达标了，但只占可写区的 0.9%

62.9 MB 校验用了 1.972 秒，而可写区有 7068.9 MB —— 抓取上限还停在
「6 处命中 × ±8 MB 求交」这个量级。既然**读几乎免费**（memcpy 级别，
64 MB 只占掉 978 ms 冻结里的一小部分），就没有理由只抓 64 MB。

改动：

- 抓取范围 = 邻域（命中点 ±8 MB）**+ 其余可写区按区域评分顺序补齐**，直到上限；
- 上限由新参数 `-snap-mb` 控制，默认 **512 MB**（原 256 MB）。

### 12.3 结论二：0.5 MB 做 50 万次校验 —— 高熵块把预算吃光

`区域扫描：读 0.5 MB｜校验 507749 次` 意味着预筛通过率 **96.8%**。

这不是 bug，是预筛判据的固有盲区：预筛看的是「像不像随机数据」，而**真正的高熵块
全是随机数据**，通过率天然接近 100%。本机实测 X25519 单次校验 **38.6 µs**
（`BenchmarkEcdhVerify`，Ryzen 7 5700X 16 线程），按 1 字节步长扫 1 MB 就要
**38 秒** —— 一块就能把整个预算吃光，这正是 11.5 秒只推进 0.5 MB 的原因。

改动（`scanBufferStat`）：

- 按 **64 KB 分段**，每段只探头部 16 KB 统计预筛通过率；
- 通过率 > 1/10 判定为高熵段，该段改用 **8 字节步长**；
- 降级块数写进报告：`高熵降级 N 块（8 字节步长）`，不隐瞒。

为什么敢用 8 字节步长：Go / C++ / Rust 的堆分配器给对象至少 8 字节对齐，
加密库的 32 字节密钥缓冲实际都落在 8 或 16 字节边界上。代价是这些段有 7/8 的
偏移没看 —— 所以只在「预筛已经失效」的段上这么做，并且逐段判断而不是整块一刀切
（一个 1 MB 块里只要有一小段压缩数据，整块降级就会漏掉其余部分里非对齐的私钥）。

### 12.4 结论三：预算重算 —— 180 秒差一点点

真实堆内存的预筛通过率是 **0.3%**（62.9 MB 只做 21.5 万次校验），
按这个速率反推：7 GB 大约 **220 秒** 能扫完。原来的 180 秒预算差一点点，
而用户恰恰是在兜底跑到一半时关的窗口。

改动：`-key-budget` 默认 **180 → 600 秒**；兜底阶段每 15 秒打一条进度
（`已读 X MB｜区域 N 个｜校验 M 次｜已耗时 T`），避免「搜索仍在进行」这一行
看起来像卡死。

### 12.5 结论四：「邻域搜索：读 0.0 MB」是纯噪音

快照已经把前三级覆盖了，`startStage = len(nearStages)` 直接跳过，于是
`nearSt` 一定是空的。这行「读 0.0 MB｜校验 0 次」会被读成「邻域搜了但什么都没有」，
而事实相反。改成：

```
[key] 邻域搜索：已在冻结副本里覆盖（跳过重复扫描）
```

### 12.6 校验顺序：先邻域、后其余

512 MB 副本不可能一次校验完，所以拆成两段：

| 段 | 内容 | 预算 | 意义 |
|---|---|---|---|
| `邻域副本` | 命中点 ±8 MB 求交 | 60 秒 | 「私钥在不在公钥旁边」一分钟内有答案 |
| `其余副本` | 按区域评分补齐的可写区 | 剩余总预算 | 抢在擦除前抓到的字节，解冻后仍可校验 |

**关键点：`其余副本` 不是重复劳动。** 快照保存的是**冻结那一刻**的字节；
解冻后如果私钥已被擦除，直接扫目标进程永远看不到它，只有副本里有。
这正是「冻结抢在 SecureZeroMemory 之前」这个机制的落地形态。

### 12.7 测试暴露的一个坑：测试 fixture 用错了

加高熵降级之后，`TestLowEntropyBlockKeepsByteStride` 一开始是**失败**的：
用 `byte(i % 251)` 填出来的「低熵」缓冲被判成了高熵。原因是周期填充在 32 字节
窗口里有 32 个不同值、零字节≈0 —— 对预筛来说它**和随机数据一样不可筛**，
通过率 100%。而真实堆内存（零填充 + 指针表）通过率只有 0.3%。

于是新增 `fillRealistic()`（零填充 + 每 8 字节一个典型堆指针），
把 `TestScanRangesUnalignedKey` / `TestSnapshotThenVerify` / `TestSnapshotSplitNearRest`
的 fixture 一并换掉。**用周期填充写的测试会反过来掩盖 bug。**

新增测试：


### 13.2 三处纯浪费

**（1）`truncated` 把 `startStage` 拉回 0 → 邻域白扫 1 分 8 秒。**

`done`**，而第 5 级 `writableRanges(regions)` 减了。450 MB 就这么被扫了两次。


### 14.4 原版的真实机制（逐函数对照）

调用图：

```
main.main.func6.3        → main.probeHint          （每收到一个包就探一次）
main.main.func6.3.5      → main.findPrivWithHints
main.findPrivWithHints   → scanHints → scanAnchors → scanWindows
scanHints                → anchor → chase
scanAnchors.func1        → anchor → chase
```

**`main.verifyPriv(priv, pub) bool`** —— 和我们**完全一致**：

```
if len(priv) != 32 || len(pub) != 32 { return false }
k, err := ecdh.X25519().NewPrivateKey(priv);  if err != nil { return false }
pk := k.PublicKey().Bytes();  if len(pk) != 32 { return false }
return memequal(pk, pub, 32)
```

反汇编里能看到 `call crypto/ecdh.(*x25519Curve).NewPrivateKey` 和
`call runtime.memequal`。所以「原版用的不是 X25519」这个猜测可以彻底划掉。

**`main.(*keySearch).check`** —— 只有 `stopped()` → 计数 → `verifyPriv` →
命中才加锁记录。**没有任何预筛**：原版不做熵判断、不做 clamp 形态过滤、
不做步长降级，每个偏移都实打实跑一次 X25519。

**`main.(*keySearch).chase.func1`** —— 指针链：

```
readBlock(addr, 8)                 // 读 8 字节
next := *(*uint64)(buf)
if next < 0x10000 || next > 0x7ffffffeffff { return false }   // 用户态校验
readBlock(next, 32)                // 在目标处读 32 字节
check(next, buf32, 32, tag="pointer")
```

**`main.(*keySearch).scanWindows.func1`** —— 真正的大范围扫描：

```
buf := make([]byte, 0x8020)        // 32800 = 32 KB + 32
for each job{lo,hi}:
    n := read(lo, buf)
    for off := 0; off+0x20 <= n; off += 0x10 {      // ← 步长 16 字节
        check(lo+off, buf[off:off+32], 32, tag="window")
    }
```

**`main.findPrivWithHints`** —— 窗口阶梯，反汇编里是三个字面量：

```
{0x2000, 0x10000, 0x100000}   =   ±8 KB  →  ±64 KB  →  ±1 MB
```

每级跑完检查 `hit`/`found`/`expired`；`expired` 就返回
`"candidate verification reached the scan deadline"`；
`[k+0xb0] == 0`（一个命中点都没有）就返回
`"handshake public key not found in readable memory"`。

### 14.5 对照表 —— 差别在这里

| | 原版 v2.0.5 | 我们（第九轮） |
|---|---|---|
| 校验算法 | `ecdh.X25519().NewPrivateKey` + `memequal` | 相同 |
| 候选预筛 | **无** | 熵预筛 + 高熵降级 8 字节 |
| 偏移步长 | **16 字节** | 1 字节（高熵块 8 字节） |
| 单块读取 | 32800 字节 | 1 MB |
| 窗口阶梯 | **±8 KB / ±64 KB / ±1 MB** | ±64 KB / ±1 MB / ±8 MB |
| 覆盖上限 | 6 处命中 × 2 MB ≈ 12 MB | 512 MB 副本 + **3.3 GB 全可写区** |
| hint 持久化 | 无（仅进程内） | 无 |
| 指针追踪 | 有（`anchor` → `chase`，读 8 字节当指针） | 无 |

**结论：原版不可能比我们「更能找到」。** 它的最大覆盖半径是 ±1 MB，
我们扫到 ±8 MB 还要再加 3.3 GB。所以「原版行、我们不行」如果成立，
唯一可能是**我们该扫的那片内存根本没扫到**，而不是我们扫得不够多。

这个推论直接指向了下面的漏洞。

### 14.6 第九轮引入的静默跳过（真 bug）

第九轮我把 `coveredNear` 从 `!snap.truncated` 改成：

```go
coveredNear := snap != nil && snap.primary > 0 && frozenNear.bytes > 0 && !frozenNear.deadline
```

**`snap.primary > 0` 不等于「邻域已经校验过了」。** `takeSnapshot` 里
`s.primary` 是在遍历到第 `primaryCount` 段时**就**记下的下标；段内如果发生
短读（`proc.ReadAt` 失败，`s.shortRead++` 后 `continue`）或尾部不足 32 字节
（`want < 32` 直接 `break`），这一段其实只覆盖了一部分，而 `primary` 仍然 > 0。

后果：**前三级邻域扫描被静默跳过** —— 不报错、不提示、日志还写着
「已在冻结副本里覆盖（跳过重复扫描）」，然后一路扫到 3.3 GB 之外，
最后报告「未找到」。这正是「一直不行」最像的样子。

修法：逐段核对，每个命中点的 `±snapshotWindow` 与可读区求交后，
必须被邻域副本**完整覆盖**才允许跳过。

```go
if prim := snap.primaryRanges(); len(prim) > 0 {
    coveredNear = true
    for _, h := range pubHits {
        for _, w := range nearRangesIn([]pubHit{h}, snapshotWindow, "chk-near", regions) {
            if !coversRange(prim, w.lo, w.hi) {
                coveredNear = false
                // 日志明说没盖住哪一段、差多少 MB
            }
        }
    }
}
```

配套：走到"没盖全"这条路时，前三级**也要 `subtractRanges(..., done)`**，
否则就退化成第八轮那种「邻域扫两次」。

同时按原版把阶梯补成 `±8 KB / ±64 KB / ±1 MB / ±8 MB`
（原版第一级就是 ±8 KB，我们之前没有；多这一级只多几毫秒）。

## 15 第十一轮：指针反查 —— 补上原版唯一一个我们没有的机制

第十轮把原版反汇编完之后，剩下一个说不通的地方：

> 原版覆盖半径不超过 **6 处 × ±1 MB ≈ 12 MB**，步长 16 字节、**没有任何预筛**；
> 我们扫 512 MB 冻结副本 + 3.3 GB 兜底，做了 5000 万次 X25519 校验。
> 原版不可能比我们「更能找到」—— 可用户实测就是原版行、我们不行。

结论只有一个：**我们该扫的那片根本没扫到**。这一轮找到了为什么。

### 15.1 根因：公钥和私钥在 Go 里是两块互不相干的内存

`crypto/ecdh.PrivateKey` 的布局（`go/src/crypto/ecdh/ecdh.go`）：

```go
type PrivateKey struct {
    curve      Curve   // 0x00，16 字节（itab + data）
    publicKey  []byte  // 0x10 ptr / 0x18 len / 0x20 cap
    privateKey []byte  // 0x28 ptr / 0x30 len / 0x38 cap
}
```

两个 slice 的底层数组是**两次独立的堆分配**，地址之间毫无关系 ——
可能相邻 32 字节，也可能隔几百 MB。

而我们在内存里扫到的那 32 字节公钥，是 `publicKey` 的底层数组。
私钥那 32 字节在另一块堆上。所以「贴着公钥扫 ±8 MB」这个思路
**在原理上就可能永远扫不到** —— 第八轮（±8 MB，21.5 万次校验）和
第九轮（±8 MB，37.5 万次校验）两次 0 命中，现在有了机制性解释，
不再是"运气不好"。

原版不靠"贴得近"，它靠**跳**。

### 15.2 原版 chase 的确切行为（反汇编 `main.(*keySearch).chase.func1`）

```
readBlock(addr, 8)                                  // 读 8 字节
next := *(*uint64)(buf)
if next < 0x10000 || next > 0x7ffffffeffff { fail }  // 用户态地址校验
readBlock(next, 32)                                 // 在目标处读 32 字节
check(next, buf32, 32, tag="pointer")               // 当候选私钥校验
```

也就是：**把某个格子里的 8 字节当指针，跟着它去校验目标处的 32 字节**。
这条路径不受任何窗口限制，可以直接跳到几百 MB 之外。

### 15.3 我们的等价实现（`cmd/collector/pointer.go`）

新增一级「指针反查」，位置在**邻域之后、区域扫描之前**：

1. 在冻结副本里**一次遍历**，找出所有 `*(uint64)q ∈ {公钥命中地址}` 的槽位 q
   （谁指向公钥字节）；
2. 从 q 往前 4 个、往后 4 个 qword 逐个当指针 t
   （`publicKey.ptr` 在 +0x10、`privateKey.ptr` 在 +0x28，相差 0x18 = 3 个 qword，
   留 4 个足够覆盖常见布局）；
3. 读 t 处 32 字节，交给同一个 `kf.Check`（和原版 chase 完全一致，
   tag 也用 `pointer`）。

成本几乎为零：反查只是 8 字节比较，**不需要 X25519**，512 MB 副本约 0.3 秒；
每个槽位只多出 9 次校验。

**一处刻意的优化（原版没有）**：反查改成多目标一次遍历。
按公钥命中逐个扫副本的话，6 处命中 × 512 MB = 3 GB 的 qword 比较，
其中 5 遍是纯重复。改成先把命中地址做成集合、一次遍历里查表，
工作量从 `O(命中数 × 副本大小)` 降到 `O(副本大小)`。

### 15.4 测试：为什么必须用合成地址

`TestScanPointersToFindsPrivBehindPointer` 一开始用真实分配，结果
**测试通过但什么都没证明** —— 日志里公钥在 `0xc00007bb78`、私钥在
`0xc00007bb58`，只差 32 字节。Go 把两个 32 字节对象放进了同一个 span 的
相邻位置，这样"命中"无法排除"其实是靠 ±32 字节的邻居碰到的"。

试过在两个 32 字节对象之间插 1 MB padding，**也无效**：
32 字节走小对象 size class，1 MB 走大对象 span，两者根本不在同一片。

最终改成**合成地址**：公钥放 `0x10000000`、`PrivateKey` 结构体放 `0x20000000`、
私钥放 `0x40000000`，三者相距 256~768 MB，全部塞进快照分片里，
`proc` 直接传 `nil`（本次所有读取都落在副本内，不该退回读进程）。
这样测试既确定、又顺带钉死了「反查不受邻域窗口限制」这件事：

```
槽位 1 个、跟踪 2 次，从 0x10000000 跳到 0x40000000（相距 768 MB）
```

`chases=2` 是对的：`k=0` 那个槽位本身存的就是公钥地址，会拿公钥当候选私钥
试一次（必然失败），`k=3` 才是 `privateKey.ptr`，第二次命中。

写测试时踩的两个坑（都已修，留在注释里）：

1. 非对齐写测试用了 `put(start+25, t2)` —— 8 字节写穿到 25..32，
   把 `start+24` 那个 qword 的低 7 字节覆盖掉了，断言直接错乱。
   非对齐标记必须落在**不覆盖**任何对齐 qword 的位置。
2. 距离断言写成 `pubAddr-privAddr < minGap && privAddr-pubAddr < minGap` ——
   `uintptr` 相减在反向时下溢成巨大值，`&&` 直接短路，断言永远不触发。
   必须用绝对值。

### 15.5 报告新增行

诊断报告的【密钥搜索】章节多一行：

```
指针反查  : 读 X MB｜指向公钥的槽位 N 个｜跟踪校验 M 次｜短读 K｜耗时 T
```

读法（也写进了分发包的常见问题 Q4h）：

| 槽位 | 含义 |
|---|---|
| 0 个 | 内存里没有任何东西引用这段公钥。多半这 32 字节不是真的客户端公钥，或已被清掉（重连再试） |
| >0 个 | 线索找到了；看「跟踪校验」有没有走完 |

### 16.2 错误一：指针反查排在 20 分钟的暴力校验后面

第十一轮把指针反查插在 `runKeySearch` 里，而 `runKeySearch` 的调用点在

现在的顺序：

```

     → 其余副本 → 区域扫描 → 兜底
```

顺带发现：反查只在**冻结副本**里做是不够的 —— 副本 465.8 MB / 可读 7516.9 MB
= 6.2%，引用公钥的结构体有 93.8% 的概率不在里面，那就会得出「槽位 0 个」的
**假结论**。所以补了 `scanPointersToLive`：直接扫活进程全部可写区域
（只读、不冻结、不挂起，7.5 GB ≈ 1.7 s）。

### 16.3 错误二：报告只在全部阶段跑完之后才记录

`keyDiagFreeze` / `keyDiagNear` / `keyDiagPointer` 原来都在 `runKeySearch`
返回后才写。用户提前关窗口 → 已经跑完的阶段结果**全部丢失**，

改成**每一级一跑完就写诊断**。另外「仍在进行」那行不再硬写"兜底没跑完"，
而是打印真实的当前阶段（这次会显示"校验冻结副本（其余可写区）"）。

### 16.4 错误三（大概率是根因）：包里有两个会话公钥，只试了一个

把现场那条握手包按 protobuf 展开：

```

19 49 f6 a0 29 01 00 10 01            f3 = steamid 76561199865868039

      08 01 12 20 e3d3923c…           f1=1, f2=32B  ← 候选 A
```

`08 01 12 20 <32B>` 就是 `CMsgSteamDatagramSessionCryptInfo`
（`key_type = 1`, `key_data = 32 字节`）。**这条包里有两条这种消息。**

`ParseHandshake` 的 `extract` 走的是「从每个 0x22 偏移试 f4→f4→f2」，

而且报告会一本正经地写「公钥在内存命中 6 处」，看起来方向完全正确。

   - 活内存里**有**槽位指向它 → 它就是客户端自己的公钥，顺着指针找私钥；
   - 活内存里 **0 个**槽位 → 不是客户端公钥，跳过。

### 17.2 但仍然没命中 —— 三个原因

槽位找到了，`跟踪校验 2 次`，全都没中。原因不在"方向"，在"窗口"：

**原因一：±4 个 qword 的依据是错的。**

第十一轮把窗口定成 ±4 个 qword（±32 字节），依据是 Go 的
`crypto/ecdh.PrivateKey` 布局（`publicKey.ptr @0x10`、`privateKey.ptr @0x28`，
差 0x18 = 3 个 qword）。

**那个依据完全不适用**：它描述的是**我们自己 Go 程序**的布局，而目标是
`cs2.exe` —— 一个 C++ 程序，根本不用 Go 的 `crypto/ecdh`。

19:10 的命中点 dump 直接证明了这点：

```

    -32  f0 92 6b a6 76 02 00 00 40 12 12 63 76 02 00 00  ← 0x276a6b92f0 / 0x2763121240
    -16  40 69 de c2 75 02 00 00 00 00 00 00 00 00 08 00  ← 0x275c2de6940
▶     +0  a6 08 1a 4a 38 f0 98 ad ...                      ← 公钥
     +32  00 00 00 00 ...（32 字节全 0）
     +64  20 cf 9f 79 76 02 00 00 00 00 00 00 00 00 08 00  ← 0x27769fcf20
     +80  00 97 a2 3a 75 02 00 00 00 97 a2 3a 75 02 00 00
```

公钥周围本身就是**一堆指针**（-32/-24/-16、+64/+80）。这是典型的 C++ 结构体，
字段偏移未知，猜 ±32 字节没有任何依据。

**原因二：只从"指向公钥的槽位"追。**

上面那个 dump 说明公钥是**内联在结构体里**的（不是被一个槽位指着）。
如果引用它的容器存的是"结构体首地址"而不是"公钥地址"，
反查就一个槽位都找不到 —— 而私钥指针可能就在公钥自己 ±256 字节内。

**原因三：只追一层。**

真实形态很可能是 `槽位 → 结构体 → 私钥指针 → 私钥字节`。
槽位直接指向的往往不是私钥本身，追一层就断了。

### 17.3 改法（`cmd/collector/pointer.go`）

```go
ptrChaseBack = 32   // ±256 字节（原 4 = ±32 字节）
ptrChaseFwd  = 32
ptrChase2Depth = 2  // 追两层
```

`chaseAt` 改成可递归的通用追法，不假设任何布局：

```go
func chaseAt(kf *keyfind.Search, r ptrReader, base uintptr, depth int, st *scanStat) (chases int) {
	for k := -ptrChaseBack; k <= ptrChaseFwd; k++ {
		slot := uintptr(int64(base) + int64(k)*8)
		t, ok := r.q(slot)
		if !ok || !isUserPtr(t) { continue }
		b := r.b32(t)
		if b == nil { st.shortRd.Add(1); continue }
		chases++
		if kf.Check(b, "pointer", t) { return chases }
		if depth > 1 {                       // 目标看起来是个结构体，再往里追一层
			chases += chaseAt(kf, r, t, depth-1, st)
		}
	}
	return chases
}
```

两个反查函数（副本版 `scanPointersTo` / 活内存版 `scanPointersToLive`）
都改成**两路追击**：

1. 从每个「指向公钥的槽位」追（原路径）；
2. 从每个「公钥命中点本身」追（新路径，对应"公钥内联在结构体里"）。

每一跳都被 X25519 校验兜住，所以放宽窗口和加深层数**不会带来假命中**，
只多花时间：每个命中点约 65 + 20×65 ≈ 1400 次校验，按 10 µs/次约 14 ms。

### 17.4 顺带修掉的两件事

**① `TestScoreRejectsRandom` 的概率性抖动。**

原来是「200 个样本、`okCount > 2` 就 FAIL」。连跑 60 次实测分布：

```
0/200 ×46    1/200 ×11    2/200 ×2
```

单样本误判率约 0.125%（Poisson λ = 0.25），`P(X>2) ≈ 0.2%` ——
一次全量回归里撞上一次就红，而代码根本没问题。这种"红灯"比不测还糟。

改成**固定种子 + 2000 样本 + 阈值 15**（0.75%，实测基线的 6 倍余量）：
同一份代码永远得到同一个 `okCount`（实测 2/2000 = 0.100%），
不存在"今天过明天挂"；而真正的回归（比如把 `ParseStream` 的 size 上限放太松）
会让误判率涨一个数量级，稳稳越过这条线。

**② 「冻结副本撞上限被截断，却仍判为已覆盖」—— 核查结论：不是 bug。**

### 18.3 空窗在哪：一个白等 1.5 秒的定时器

`startKeySearch` 里原来是这段：

```go
drain := time.NewTimer(1500 * time.Millisecond)   // 等同一个包里其它候选
```

它等的位置**在 freeze 之前**。而候选其实是**同一个收包回调里连续投进来的**：

```go
case s.targetPubCh <- info.PublicKey:            // 主候选
...
for _, c := range handshake.ByteFieldCandidates(udp.Data, 32) {
    case s.targetPubCh <- c:                     // 同包其它 32 字节字段
}
```

两次投递相隔几微秒，通道有 16 个缓冲、投递方从不阻塞。
那 1.5 秒里 99.99% 是纯白等。

而 Steam 数据报的会话私钥**只活一次 RTT**：客户端发出 ClientHello
（就是被我们认出来的那个 c2s 包）→ 收到 ServerHello → 用它算出共享密钥
→ `SecureZeroMemory`。RTT 几十毫秒。

1.5 秒的空窗，足够私钥在冻结之前消失两次还有余。

**① 收集判据从「等满固定时长」改成「等静默」。**


压了 125 倍。12 ms 对微秒级的投递间隔有 3 个数量级余量。

**② 把「抢跑延迟」变成可实测的指标。**

新增 `pubSeenAt`（在 c2s 包里认出公钥的时刻）→ `searchKey` 进来时


### 19.2 硬结论一：兜底那一级撞的是算力墙，不是 IO 墙

日志里那个「预计还需 49m4s → 1h5m15s」看起来像是"读得慢"，于是第一反应
会是加线程、加大缓冲、改块大小。**这个方向是错的，而且可以实测证伪。**

写了个独立基准（`D:\tmp\xb\main.go`，Go 1.24.4，`crypto/ecdh` X25519）：

```
NumCPU = 16
单核单次 = 37.987µs
workers= 1  4096 次 in    159ms =>     25778 次/s
workers= 2  4096 次 in     80ms =>     51119 次/s
workers= 4  4096 次 in     40ms =>    102239 次/s
workers= 8  4096 次 in     32ms =>    127025 次/s
workers=16  4096 次 in     21ms =>    190537 次/s   ← 16 核只有 7.4 倍
若扫    6311 MB：约  509.6 M 次校验 → 44m34s
```

再看现场那一行：`32 MB / 2,586,587 次校验 / 15 s` = **172,439 次/s**。
峰值 190,537 次/s 的 **90%**。

也就是说：

- 兜底阶段**已经贴着算力墙在跑**，加线程/加缓冲的收益上限是 10%；
- 49 分钟的 ETA 是真的，不是估算错误；
- 6.3 GB 逐字节全扫，在这台机器上**物理上就是 44 分钟**。

`numWorkers()` 上限 32、`runtime.NumCPU() = 16`，本来就吃满了。

**还有一个更致命的**：这一级扫的是**解冻之后的活内存**，不是冻结那一刻的副本
（副本只有 512 MB，装不下 6.3 GB）。私钥若在冻结时还在、冻结后又没被擦，
那也该在副本里找到；副本里没有，说明冻结那一刻就已经没了。所以这一级
**结构上不可能成功**，不只是慢。

结论：兜底这一级从"能救命"降级为"确认性动作"。现在它在开跑前就会用
实测吞吐算出可行性，扫不完就直接说：

```
[key] ⚠ 这一级按实测算力（19 万次 X25519/s，预筛通过率 7.7%）需 44m34s，
      而预算只剩 19m58s —— **本次扫不完**，最多覆盖 45%。
[key]   → 结论：兜底这一级救不了场。私钥若真在这 6311 MB 里，也早被解冻后的
      客户端擦掉了（它扫的是活内存，不是冻结那一刻的副本）。
```

### 19.3 硬结论二：19 ms 里有 12 ms 是纯死等

`freezeRun` 是先 `fz.FreezeFast()`（`NtSuspendProcess`）再跑闭包的，
而 `locatePub`（扫 7.4 GB）和 `takeSnap` 都在闭包**内部** —— 也就是说
进程在 T+19 ms 就已经停住了，之后扫多久都不会让状态继续变化。

所以报告里那 2 处 `+32 全 0` 是 **T+19 ms 的冻结状态**，不是后续漂移。
**客户端在公钥上网之后 19 ms 内就把私钥清零了。**

19 ms 的构成：

| 段 | 耗时 | 能不能砍 |
|---|---|---|
| `collectBatch` 的静默窗口（等候选） | 12 ms | **能，这是纯死等** |
| `FreezeFast`（遍历全部线程挂起）+ 调度 | ~7 ms | 难，是挂进程本身 |

候选是在同一个收包回调里连续投进来的（`s.targetPubCh <- info.PublicKey`
紧接着 `for _, c := range ByteFieldCandidates`），两次投递相隔几微秒，
通道有 16 个缓冲、投递方从不阻塞。12 ms 对微秒级间隔有 3 个数量级余量，
**纯属白等**。

改成 1 ms。同时新增「握手→冻结延迟」指标 —— 之前只量到 `searchKey` 进门，
那时进程还在跑，不是真正的计分点：

```
[key] 握手→搜索延迟：8ms（越短越好；私钥只活一次 RTT，几十毫秒量级）
[key] 握手→冻结延迟：15ms（真正的计分点；其中挂进程本身占 700µs）
```

两行之差直接告诉下一轮该优化哪一段：如果 `挂进程本身` 就有 5 ms，
那再怎么砍等待也到不了 2 ms，得换成按线程 `SuspendThread` 并行挂。

### 19.4 硬结论三：命中点变成异构了

20:18 的 7 处命中点，形状**不再统一**：

| 命中地址 | `+32` 判读 | 说明 |
|---|---|---|
| `0xa83c56e03c` | **高熵** | 区域只 20 KB；窗口内另有 12 个像私钥的块 |
| `0x20cec8f83c4` | 既非全 0 也非私钥 | 后面跟着 `Windows\System3...` 宽字符串 → 普通堆对象 |
| `0x20cec8fa784` | 既非全 0 也非私钥 | 同上 |
| `0x20ced9d07a0` | **全 0** | ← 密钥结构体 |
| `0x20ced9d0ed0` | **全 0** | 前后 ±64 全 0 |
| `0x20d79830e70` | 既非全 0 也非私钥 | |
| `0x20d81acdbe0` | 既非全 0 也非私钥 | `+48` 有 `ff ff ff ff` 幂等标记 |

所以第十四轮那句「两次现场同一形状基本定案」要**收窄**：

- 能证明「客户端在这个结构里存过私钥、并且已经擦掉」的，只有那 2 处全 0；
- 另外 5 处是噪声（报文副本、普通堆对象），**不能拿它们反过来否定"私钥已擦"**。

同时 7 处里有 3 处带报文特征（`命中性质：3 处是报文副本，4 处不是`），
和之前的观察一致。

### 19.5 一个假 bug：槽位值 = 0x0

报告里这一条，看着像反查算法坏了：

```
0x20ced9d0d68　PRIVATE　区域 0x20ced9c5000 + 128 KB
▶     +0  00 00 00 00 00 00 00 00 01 00 00 00 00 00 00 00
    槽位值 = 0x0（非用户态地址（不像指针））
```

一个「值等于公钥地址」的槽位，值怎么可能是 0？

**反查没错。** 槽位是在**冻结那一刻的副本**里反查出来的，
而 `formatSlotDump` 读的是**解冻后一分钟的活内存** —— 那个对象早被释放/复用了。
两个数据源不同时间，结论自然对不上。

同一份报告里的另一条恰好证明反查是对的：

```
0x20cea9fa5a0　PRIVATE　区域 0x20cea9f8000 + 12 KB
▶     +0  e0 db ac 81 0d 02 00 00 c0 a9 94 20 0c 02 00 00
    槽位值 = 0x20d81acdbe0（→ PRIVATE 区域 0x20d81acc5000 + 64 KB）
```

`0x20d81acdbe0` 正好是第 7 个公钥命中点。

修法：`formatSlotDump` 增加 `snap` 参数，**优先从冻结副本读**（那是权威的），
同时把活内存的值附在后面；不一致时明说是"冻结后被改写"，
而不是让它看起来像 bug。新增 `snapRead`：只在整个区间被同一个 chunk
完整覆盖时才返回，跨边界一律退回活内存（半截数据比没有更危险）。

顺带一提，20:18 报告里 `0x20d489dcc08` 那个槽位（候选 `e3d3923c…` 的）
`+32` 之后是 96+ 字节连续高熵，X25519 没过（2081 次校验里包含它）。
它指向的 `0x20d489dc8c0` 是候选自己的公钥命中点，而高熵段在
`槽位 + 0x368` 处，不是相邻字段 —— 更像一块加密载荷缓冲区，不是私钥。

## 20 第十六轮：21:01 现场 —— 账号被封，以及一个决定性的技术反转

> 这一节先说事故，再说技术。事故的结论会直接决定技术路线。

### 20.1 事故：测试账号被封

2026-10-17 21:01 那次运行之后，用户账号被封禁。

**当时用的是默认的 `-freeze full`**，冻结 1.979 秒。

程序对 `cs2.exe` 做的三件事，按可疑程度排序：

| # | 动作 | 为什么可疑 |
|---|---|---|
| 1 | `NtSuspendProcess` 挂起**全部线程** ~2 秒 | VAC 自己跑在游戏进程里的线程也在里面 → VAC 看到自己的心跳/计时器断了近 2 秒。这**不是"读内存"，是"让反作弊停摆"** |
| 2 | 外部进程持有 `PROCESS_VM_READ` 句柄 | VAC 的内核组件能枚举到这种句柄 |
| 3 | 连续 `ReadProcessMemory` 扫 7.5 GB | 读取模式本身不像正常软件 |

第 1 条是主因的判断依据：

- 它不是"多读了一点"，而是**一个明确的异常状态**；
- 冻结发生在**握手那一刻**，也就是客户端正在连服务器的瞬间 ——
  这是最被关注的时刻；
- 同一天跑过 5 次（18:47 / 19:10 / 19:46 / 20:18 / 21:01），
  每次冻结 1.8~2.4 秒，**累计异常**；
- 用户硬约束是"安全为主要条件"，而这条恰恰是最不安全的一步。

必须写清楚的一点：**"只读、不注入、不建远程线程、不写内存"这几条底线
这一版没有变，但它们不等于"看不见"。** 只读句柄 + 冻结线程都是可见的。

处置（已落进代码）：

| 改动 | 说明 |
|---|---|
| `-freeze` 默认值 `full` → **`off`** | 不冻结，异常面最小；要冻必须显式加参数 |
| 冻结前 stderr 大声警告 | 之前用户根本不知道每进一次对局都在挂起全部线程 |
| 诊断报告最前面加【⚠ 封号风险】 | 打开报告第一眼就看到，不是藏在末尾 |
| `使用说明.txt` 开头加封号警告 + FAQ Q0 | 三条硬性要求：小号 / 不进 VAC 服务器 / 不用 full |

### 20.2 技术结果：6 ms 达成了，但目标根本不在那儿

先看好消息 —— 第十五轮那 1 ms 的改动**完全生效**：

```
[key] 握手→搜索延迟：6ms（越短越好；私钥只活一次 RTT，几十毫秒量级）
[key] 握手→冻结延迟：6ms（真正的计分点；其中挂进程本身占 0s）
```

19 ms → **6 ms**，`挂进程本身` 甚至测不出来（<100 µs）。时间窗这条线已经到头了。

然后是坏消息。6 ms 时 7 处命中点的判读：

| 命中地址 | 前面的字节 | `+32` 判读 | 真相 |
|---|---|---|---|
| `0xb8e97ee23c` | `3a 75 0a 31 08 01 12 20` | **高熵** | **报文副本**，后面是密文载荷 |
| `0x2aee45e0dd0` | `00 00 00 00 00 00 08 00` | 全 0 | 密钥结构体，私钥槽是空的 |
| `0x2aee45e12d0` | `00 00 00 00 00 00 08 00` | 全 0 | 同上 |
| `0x2af389f7204` | `... 08 01 12 20` | `19 1d 97 91 79 84 e1 d7 3e 20 0d 28 02` + `ff ff ff ff…` | **哈希表**（`ff ff ff ff` 是空槽标记） |
| `0x2af504fcdc4` | `... 08 01 12 20` | **同样** `19 1d 97 91 79 84 e1 d7 3e 20 0d 28 02` | 同一张哈希表的另一个实例 |
| `0x2af6fff5930` | `... 08 00` | 全 0（`-48` 起是 `ff ff ff ff`） | 也是表结构 |
| `0x2af70d6c770` | `04 11 94 e2…`（另一个公钥的尾巴） | `b0 d8 93 e0 fd 7f 00 00` | 是个指针，不是密钥 |

三个决定性的观察：

**(a) `0x2af389f7204` 和 `0x2af504fcdc4` 的 `+32` 是同一串 14 个字节**
（`19 1d 97 91 79 84 e1 d7 3e 20 0d 28 02`）。**两处完全相同的字节不可能是私钥** ——
私钥是随机的，撞不出一样的前 14 字节。那是固定结构（哈希/表头）。

**(b) 那个"高熵"是判读的假阳性。** `0xb8e97ee23c` 前面是
`3a 75 0a 31 08 01 12 20` —— protobuf 字段头。这处是**握手包在内存里的副本**，
公钥后面当然紧跟整段密文载荷，熵必然高。把它报成"疑似私钥"会把人引向错误偏移。

**(c) 6 ms 已经等于 ClientHello 刚上网。** 这个时刻私钥**不可能**已经被擦
（客户端还没收到 ServerHello）。所以 `+32` 全 0 不是"擦除得太快"，
而是**那个位置本来就不是私钥槽**。

### 20.3 定案：`pub[32] + priv[32]` 这个假设死了

前面四轮（13~16）整条路线都建立在同一个假设上：

> 客户端把会话密钥对存成 `pub[32] + priv[32]` 的连续结构体，
> 所以贴着公钥扫就能找到私钥，找不到就是"擦得太快"。

现在这个假设被三份独立证据推翻：

1. 6 ms 冻结时 `+32` 仍然全 0（时间上不可能是擦除）；
2. 那些"高熵"其实是报文尾部密文和哈希表字段（内容上不是私钥）；
3. 两处不同命中点的 `+32` 是**同一串字节**（随机性上不可能是密钥）。

所以：

- 「让冻结更早」这条线**已经走到头**（19 ms → 6 ms，再快也没有意义了）；
- 「贴公钥扫 ±8 MB」这条线**也走到头**（三次现场 0 命中，不是因为窗口不够宽）；
- 继续在这条路上加码，只会增加封号风险而不会提高命中率。

### 20.4 转 B 方案：直接找对称会话密钥

第十五轮 19.8 事先写好的判据是：

> 进了 10 ms 但仍全 0 → **立即转 B：直接找共享密钥**。

现在条件完全满足（6 ms + 全 0）。而且 B 方案有一个 A 方案永远没有的好处：

| | A：找 X25519 私钥 | B：找对称会话密钥 |
|---|---|---|
| 存活时间 | 一次 RTT（几十毫秒） | **整个会话**（几十分钟） |
| 需要竞速 | 是，毫秒级 | **不需要** |
| 需要冻结 | 是 | **不需要** |
| 封号风险 | 高（挂起全部线程） | **低（只读）** |

**B 方案天然不需要冻结** —— 这一条同时解决了技术问题和安全问题。

B 的技术前提：客户端算出共享密钥后，会把它（或它的派生 AES key）
存进会话状态对象，并在整个会话里反复使用。找它不需要赶时间，
可以在**主菜单/大厅**从容地扫，扫多久都行。
